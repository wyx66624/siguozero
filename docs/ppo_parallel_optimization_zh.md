# PPO 并行环境、学习端优化与 30 亿步工期

2026-09-11，四暗 main、死规则开启，RTX 4090 24 GB。
本轮已经实现 CPU 多进程在线环境、直接因果 SDPA、增大学习微批及关闭激活重算。
棋盘 128 + 动作 128、时序 256 维、32 层、FFN 1024、历史上限 1000 步保持一致。
仍有独立 Policy/Critic，每个优化器小批 512 个真实决策，两者各 3 个 epoch。

最终代码连续 12 轮完整训练测得 **147,456 个环境动作 / 298.13 秒 = 494.60 步/秒**，
对应单模式 30 亿步约 **70.20 天连续运行，或 87.75 个日历天（80% 可用时间）**。
这是按实测对局分布的条件外推，已包含实际出现的满窗口重算和两次正常布阵更新。
原始记录见[最终 12 轮实测](benchmarks/ppo_parallel_g48_final_4090_20260911.json)，
可复算汇总见[工期 JSON](benchmarks/ppo_parallel_training_eta_20260911.json)。

| 配置 | 完整训练吞吐 | 30 亿步连续天数 | 80% 可用时间的日历天数 |
|---|---:|---:|---:|
| 上一轮：串行环境、微批 8 | 236.78 步/秒 | 146.64 | 183.31 |
| 学习端优化，环境仍串行 | 358.80 步/秒 | 96.77 | 120.97 |
| 本轮最终：学习端优化 + 4 进程环境 | **494.60 步/秒** | **70.20** | **87.75** |

相比上一轮完整窗口，吞吐约为 **2.09 倍**，条件工期减少约 **52.1%**。
同检查点第一轮对照为 46.68 → 29.92 → 21.30 秒：
学习端约 1.56 倍，再增加环境并行约 1.40 倍，组合约 2.19 倍。
跨多轮时 BF16 舍入会改变后续棋谱，因此这些窗口均值不代表严格相同的全部动作序列。

## 已落地的改动

| 原瓶颈 | 当前实现 |
|---|---|
| 主进程逐局执行规则、生成四席观察 | 4 个常驻 CPU 进程各自维护一组独立棋局；每步只交换动作、合法动作和新增 int16 观察行 |
| 每轮/每次换局重复传输静态棋盘图 | IPC 只序列化可变规则状态；每个进程复用按游戏类型缓存的静态棋盘拓扑 |
| GPU 等待 CPU 推进环境 | 发出动作后，CPU 进程推进棋局，同时主进程运行冻结 Critic；收到结果后再提交下一波 Policy 采样 |
| 每次反传最多 8 条历史 | main 默认增至 32；每次 Adam 更新的监督决策数仍为 512 |
| 每层激活重算 | 四国默认关闭，保留 CLI 开关和单卡 OOM 整批重试 |
| 注意力掩码构造、合并和转换 | 时序网络直接调用 `scaled_dot_product_attention(is_causal=True)`，使用原有 QKV 和输出投影权重 |
| 每个微批在反传前转 CPU 指标 | 梯度累积后一次性提取该优化器小批的指标 |
| 旧检查点恢复后仍锁在微批 8 | 旧有效值等于旧配置值时接受新配置；曾因 OOM 缩小的有效值继续保留 |

每局内部仍按合法行动顺序推进，跨局在多个进程中并行，避免 Python 线程锁限制。
GPU 模型、布阵采样和随机数状态留在主进程，子进程只接收规则游戏对象。
采集结束时把完整游戏状态同步回主进程，继续使用原有检查点格式；测试覆盖终局换局、
未满一波的采样批、队伍视角奖励与 GAE、历史滑窗、进程异常和退出清理。

右侧 padding 的有效查询只能注意到自身以前的位置，因此直接因果 SDPA 不需要额外的
padding 掩码；无效输出仍归零。模型参数名称和张量形状兼容已有 compact 检查点。
FP32 数值与梯度检查通过；BF16/原子归约的舍入差异可能改变之后的随机采样棋谱，
因此多轮 A/B 用于性能比较，不声称逐步位级等价或棋力提升。

## 对照方法与计算口径

三组均在本机 WSL Ubuntu 24.04、PyTorch 2.11.0+cu130、RTX 4090 上测量，
4 个 PyTorch CPU 线程，CUDA 分配器上限 90%，GPU 测量串行执行并持有独占锁。
从同一只读四暗 update 4 检查点恢复权重、优化器、随机状态和 40 个未结束棋局，
计时前用相同方法补齐至 48 局。每轮精确执行 12,288 个新环境动作。

- 上一轮串行环境、微批 8：[4 轮 236.78 步/秒](benchmarks/ppo_pipeline_g48_after_4090_20260911.json)。
- 只启用学习端优化，环境仍串行：[4 轮 358.80 步/秒](benchmarks/ppo_parallel_g48_learner_only_4090_20260911.json)。
- 学习端优化与多进程环境组合：[最终 12 轮 494.60 步/秒](benchmarks/ppo_parallel_g48_final_4090_20260911.json)。

在剔除静态拓扑传输前，两组并行实现的复测分别是
[12 轮 457.78 步/秒](benchmarks/ppo_parallel_g48_after_4090_20260911.json)和
[8 轮 475.14 步/秒](benchmarks/ppo_parallel_g48_verified_4090_20260911.json)。
完整状态同步从每轮约 1.3 秒降至最终平均 **0.18 秒**。
最终 12 轮平均每轮 24.84 秒，实际分配显存峰值 **13.79 GiB**、
分配器保留峰值 **20.39 GiB**，学习微批保持 32，actor/critic batch 保持 48。

三者每轮 Policy/Critic **各执行 72 次优化器 step**，没有减少 epoch 或因 KL 提前停止。
布局更新按原来每 8 轮的节奏执行。计时包括规则推进、观察编码、采样、Critic 推理、
GAE、Policy/Critic 学习、布阵更新、图捕获、日志及循环收尾。
各轮均使用实际 environment_plies，梯度累积或重复 epoch 不增加环境步计数。

检查点加载和计时前补局不计入长期吞吐；完整训练探针未写入模型参数，源检查点大小和
修改时间保持不变。微型分布式恢复验证使用独立测试目录内的临时检查点。

## 满窗口与剩余瓶颈

最终 12 轮真实对局中出现 **33 个 1001 token 满窗口样本**，占 147,456 个样本的约 0.0224%。
窗口滑移已进入端到端计时，但这不是长期训练后滑窗占比的保证。
滑移后，旧观察离开窗口、局部位置编码重新排列，已有 KV 不能直接精确复用；
当前用更快的因果 SDPA 执行全窗口计算，继续保持原观察语义。

容量验证让三套 Adam 状态和 Layout reference 同时驻留：

| 压力场景 | 测量 |
|---|---|
| 32 条独立历史，各 1001 token，合计 512 个前缀决策 | Policy/Critic 峰值分配约 15.29 GiB，微批维持 32 |
| 48 局对应的 192 个玩家历史，双模型满窗口推理 | actor/critic batch 均维持 48，峰值分配约 13.57 GiB |
| 192 个历史同时滑移一格，双模型重新计算 | 约 2.39 秒；缓存输出与清缓存后的完整前向比较通过 |
| 512 个滑窗决策，前缀不能合并，Policy/Critic 各 1 个 epoch | 约 3.09 / 3.03 秒；512 条独立窗口，复用率 0，微批维持 32 |

这是合成观察的显存/重算压力测试，不是合法对局吞吐或棋力测试。
原始数据见[满窗口压力验证](benchmarks/ppo_parallel_capacity_verified_4090_20260911.json)，
工具也测量 512 个无法合并前缀的滑窗决策，明确区分“前缀可合并”和“滑窗不可合并”。

本轮不能把 30 亿步承诺为 10–20 天：20 天需要持续 1736 步/秒，15 天需要 2315 步/秒。
按最终吞吐，20 天仍需再提高约 **3.51 倍**。平均每轮 Policy/Critic 学习合计 **13.71 秒**，
约占整轮 **55.2%**；在线采集合计 **10.33 秒**，其中 Policy 推理 **2.91 秒**、
Critic 推理 **2.54 秒**、未被推理遮盖的环境等待/写入/换局 **4.59 秒**。
四个环境进程的累计计算时间均值为 9.72 秒，属于重叠的 CPU 工作量，不能再次加到整轮墙钟时间中。
如果后期大部分棋局超过 1000 步，整窗重算和前缀复用下降会使上述工期增加。

当前每 5000 万步进行一次 100 局评测，共 60 次。训练时间表未包含这些独立评测与保存，
若每次实际耗时 E 秒，额外连续时间为 `60 * E / 86400` 天；80% 可用率再除以 0.8。
这里不使用理论 FLOPs 或其他显卡的宣传算力推算。双明共用优化代码，但本次时间测量仅针对四暗。

## 默认配置、验证与复现

默认配置位于 `configs/bootstrap.yaml` 的 `ppo` 节：

```yaml
environment_workers: 4
learner_microbatch_by_model_scale:
  main: 32
causal_sdpa: true
activation_checkpointing: false
```

`bash scripts/start_four_player_ppo.sh four_dark` 使用这些新配置。
`ENVIRONMENT_WORKERS=1` 切回串行环境；`MICROBATCH=8` 可缩小反传批；
CLI `--activation-checkpointing` 恢复重算，`--no-causal-sdpa` 使用旧注意力路径。
这些开关不修改模型维度。暂停的二人训练未启动，二人模型继续使用既有 GRPO 路径。

验证结果：**250 项测试、281 个子测试通过**；双进程 CPU DDP 每个 rank 使用 2 个环境进程，
验证两轮 PPO、计划内评测保存、恢复游戏池与模型、两 rank 参数一致。
静态拓扑传输优化后，53 项相关回归及 28 个子测试通过，并再次通过双进程恢复验证。
见[分布式恢复记录](benchmarks/ppo_parallel_distributed_transport_20260911.json)。
启动脚本通过 `bash -n`，仓库差异通过 `git diff --check`。

复测工具 `tools/benchmark_ppo_pipeline_update.py` 可指定 `--environment-workers 1/4`，
采用 `--games 48 --moves-per-game 256 --updates N`；源检查点、源码指纹、显存峰值、
每轮真实样本数和优化器更新次数随 JSON 保存。
`tools/verify_ppo_parallel_capacity.py` 验证满窗口容量、滑移重算和缓存一致性。
`tools/estimate_ppo_parallel_runtime.py` 根据测量数据计算阶段对照与工期，不采用猜测的加速比。
