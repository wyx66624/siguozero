# 训练性能优化复盘：瓶颈、实现与验证

整理日期：2026-09-12。

本文汇总此前从计算量核查、模型编码简化，到历史数据整理、在线环境并行、GPU 学习与 KV 缓存优化的工作，说明每一步为什么做、怎样实现、实际收益和剩余限制。

**历史最快完整训练探针为 1,273.13 个环境动作/秒，30 亿步条件外推约 27.27 天连续训练，20 天目标尚未达到。** 这来自 2026-09-11 的四暗 main、单张 RTX 4090 24 GB 测量，并非当前训练的实时剩余时间。根据910B算力和显存远超过4090，因此相同计算量应该可以压缩至一周以内。

性能记录主要对应 revision 20–22 的实现演进。后续已经增加 [70 步无吃子和棋规则](draw_rule_migration_zh.md)和 [revision 24 和棋负奖励、六维动作输入](draw_penalty_countdown_zh.md)，会影响局长、数据分布和模型计算；这些改动后的长期吞吐需要重新测量。本文保留旧结果的版本和统计口径，不把历史验证当作新版验证。

## 1. 目标与计算口径

目标是四暗单模式累计 **3,000,000,000 次真实环境动作**。一次实际 `game.step()` 算一步，所有棋局、席位和 rank 合计；四位玩家各走一手就是四步。Policy/Critic 前后向、GAE、bootstrap 和重复训练 epoch 不增加步数。

```text
20 天连续运行所需吞吐 = 3,000,000,000 / (20 × 86,400)
                     = 1,736.11 个环境动作/秒

若要求 20 个日历天完成、机器有效可用时间为 80%：
训练运行期间需达到约 2,170.14 个环境动作/秒，评测与保存开销仍需计入。
```

此前截图中的语言模型估算 `C ≈ 6ND`，在 `N=1B、D=26B` 时得到 `1.56×10²⁰ FLOPs`。这个数可以用来比较计算规模，但不能直接给出本项目的训练天数，原因有三类：

- **工作量不同。** 一个环境动作要经过在线采样，并进入独立 Policy 和 Critic 的学习；两个模型各做 3 个 epoch。同一次决策还可能包含一段历史，历史前缀是否能合并决定实际执行多少计算。
- **执行形态不同。** 32 层、较窄的时序网络产生许多小算子，Python 调度、GPU 内核启动、张量转换、同步和显存访问会占用时间。大矩阵乘法的吞吐不能代表整段训练吞吐。
- **训练闭环包含其他阶段。** 规则推进、观察生成、布阵、终局换局、历史维护、评测及检查点都需要时间；其中一部分无法与 GPU 计算重叠。

因此，工期以完整训练轮的真实动作数和墙钟时间计算。详细背景见[旧计算量剖析](game_ai_training_compute_comparison_zh.md)和[小宽度模型瓶颈诊断](compact128_training_bottlenecks_zh.md)。

## 2. 优化是怎样逐步推进的

| 阶段 | 发现的问题 | 采取的方向 | 证据边界 |
|---|---|---|---|
| 编码结构简化 | 每个历史棋盘都经过逐点 Transformer，计算量远大于参数占比所暗示的成本 | 整盘 one-hot 单层投影；动作坐标单层投影；四国改为 128＋128 维 token | 改变模型结构，不能当作只改变执行速度 |
| 数据通路整理 | 反复遍历历史、建小张量、拼接与上传，GPU 经常等输入 | 数组历史、精确前缀合并、成块编码、固定 KV、批量动作损失 | 同检查点 2,560 步诊断轮 56.05 → 19.16 秒 |
| 在线环境并行 | GPU 采样后，主进程逐局执行规则与观察 | 常驻 CPU 多进程、紧凑 IPC；配合微批 32、关闭重算和直接因果注意力 | 历史 48 局完整窗口吞吐约 237 → 495 步/秒 |
| 向 20 天目标推进 | 数据上传、布阵、学习调度与在线等待仍明显 | 编码块 2048、布阵预取、变长注意力、编译、融合优化器、两组流水、批量 Critic | 同一稳态统计法：48 局约 71.46 → 33.54 天；96 局大采样约 27.27 天 |
| 长局与运行保障 | 满窗口破坏复用；训练需要持续运行与独立评估 | 多 query KV、窗口重建验证、监控服务、CPU 对弈副本 | 长局仍是主要不确定项；服务化本身不等于 GPU 加速 |

这些阶段存在不同模型、采样规模和测量窗口，不能把每行的局部倍数相乘，得出一个总加速倍数。

## 3. 模型编码：先减少真正昂贵的计算

### 3.1 棋盘由逐点 Transformer 改为整盘线性编码

旧实现为每个棋盘建立点位向量，再经过 8 层棋盘 Transformer。历史越长、重复编码越多，这部分越昂贵。

revision 20 改为：按原有玩家视角和可见性规则生成固定顺序的棋盘类别 one-hot，拼入模式和可选阵亡信息，再用一个可训练 `Linear` 得到整盘向量。去掉逐点 Embedding、棋盘注意力、池化和逐点输出。

按 revision 20 的 256 维输出核算，单棋盘主要前向矩阵计算约由 **2.319 GFLOPs 降至 0.00922 GFLOPs**，约为原来的 1/252。这只针对棋盘编码器，不能当作整轮加速比；时序网络、环境和数据展开仍有成本。

实现与计算式见[整张棋盘单层编码](whole_board_linear_zh.md)，代码集中于 [models.py](../src/junqi/training/models.py)。

### 3.2 动作与时序宽度简化

revision 21 使用 `[起点 x, 起点 y, 终点 x, 终点 y, 相对玩家]` 的单层投影替代多字段 Embedding。revision 22 将四国的棋盘和动作输出各改为 128 维，拼成 256 维时序 token，main 保持 32 层、FFN 1024。

这类修改直接减少模型计算，但也改变表达能力，需要按结构版本处理检查点，并用棋力评测判断训练效果。**当前 revision 24 已增加第六项无吃子倒计时；五维描述仅适用于当时的性能基线。** 详见[动作输入演进](action_linear_zh.md)。

## 4. 历史与数据准备：减少重复劳动

原通路为每个决策遍历历史记录、生成 Python 对象和小张量，再逐项上传。即使数学计算可以复用，数据准备仍然重复执行。

具体改动如下：

1. **数组历史。** 使用预分配的整数块追加观察，学习样本引用只读窗口。窗口移动时保留仍被学习样本引用的块，避免覆盖旧样本。
2. **缓存身份。** 用棋局身份、席位、窗口起点、长度和模型版本定位复用范围，减少对整段记录反复求哈希；仍保留精确前缀条件。
3. **前缀合并。** 同一玩家已发生历史中的多个决策，共享一次因果序列编码，在各自位置取输出计算损失。
4. **批量张量处理。** 保留二维编码块，通过拼接和索引收集得到学习输入；合法动作、条件动作头、log-probability、熵和 PPO 损失尽量按批计算，指标在累积后集中取回 CPU。

早期固定输入诊断中，热采样的 `torch.tensor` 调用由 **1,176 次降至 7 次**，学习准备的 `as_tensor` 调用由 **31,527 次降至 0 次**。同检查点完整 2,560 动作诊断轮由 **56.05 秒降至 19.16 秒，约 2.93 倍**；该窗口包含优化器更新，但未跨越评测、保存或布阵更新。

这些数字说明数据整理有实际收益，不代表所有阶段都以相同比例加速。实现见 [history_arrays.py](../src/junqi/training/history_arrays.py)、[models.py](../src/junqi/training/models.py)、[ppo.py](../src/junqi/training/ppo.py)，完整证据见[数据通路优化报告](ppo_pipeline_optimization_zh.md)。

## 5. 在线环境：从逐局串行到跨局并行和流水

### 5.1 常驻 CPU 进程推进独立棋局

旧流程中，主进程完成一批 GPU 采样后，逐局执行规则、生成各席观察、维护历史，然后才能继续采样。增加 GPU 算力无法消除这段等待。

新的 `ParallelPPOEnvironment` 将独立棋局分配给常驻 CPU 进程。默认配置使用 **4 个进程、48 局**；吞吐配置使用 **8 个进程、96 局**。GPU 模型和布阵采样留在主进程，子进程处理规则状态，并返回动作执行结果、合法动作和新增数值观察。

关键实现不是每步临时启动进程，而是复用进程和棋局状态：

- IPC 仅传输必要的可变状态；静态棋盘拓扑按模式在各进程缓存，避免重复序列化。
- 观察直接生成紧凑的数值行，减少 `ObservedPiece`、`ObservedEvent`、`StateTokenRecord` 等中间对象；沿用原有可见性判断。
- 同一局仍严格按行动顺序推进，独立棋局之间并行。返回结果核对棋局索引和完整性，避免把动作或奖励接到错误棋局。
- 在采集边界同步完整棋局状态；检查点继续保存未完成棋局、历史和随机状态，并覆盖异常退出清理。

剔除静态拓扑重复传输后，历史测试中的每轮完整状态同步约由 **1.3 秒降至 0.18 秒**。代码见 [ppo_environment.py](../src/junqi/training/ppo_environment.py)、[packed_observation.py](../src/junqi/training/packed_observation.py)，完整测量见[并行环境报告](ppo_parallel_optimization_zh.md)。

### 5.2 用两组棋局隐藏 CPU/GPU 等待

多进程之后，CPU 规则与 GPU 推理仍可能轮流等待。后续将棋局分成两个独立调度组：A 组动作提交给 CPU 后，GPU 计算 B 组动作；收到 A 组结果后，再继续 A 组下一次决策。

```text
原流程：GPU 推理全部棋局 → CPU 逐局推进 → GPU 下一批推理

两组流水，时间向右：
GPU：   推理 A 组       推理 B 组       推理 A 组下一手
CPU：                  推进 A 组       推进 B 组
                       └ 同期重叠 ┘    └ 同期重叠 ┘

只有独立棋局组可以重叠；某局自己的下一手必须等上一手完成。
```

第一阶段用冻结 Critic 推理填补部分 CPU 等待。后续进一步启用 **延后 Critic**：采样时保存原状态和转移，采样结束后用尚未更新的 Critic 批量计算状态价值与 bootstrap，再形成 GAE。这样减少逐波价值推理的小批开销，同时让 Actor 更适合两组流水。

整个采样轮冻结 Policy；价值计算必须基于原状态和正确的模型版本。保留奖励、终局、队伍视角与 PPO clipping 的对应关系。实现见 [ppo_pipeline.py](../src/junqi/training/ppo_pipeline.py) 的 `collect_pipelined` 及 [ppo.py](../src/junqi/training/ppo.py)。

## 6. GPU 学习：扩大有效计算批量，减少启动和搬运

### 6.1 微批、激活重算和注意力

学习微批从 **8 条历史增至 32 条**，提高每次 GPU 调用的工作量；每次优化器更新仍监督 512 个真实决策，Policy/Critic 仍各做 3 个 epoch。这里增大的是执行微批，不是把训练预算减少四倍。

在 4090 显存允许的配置下关闭逐层激活重算，减少重复前向；保留 OOM 后缩小有效微批重试的能力。注意力先改为直接因果 SDPA，减少掩码构造与转换；后续使用变长 Flash Attention 打包有效 token，减少长短历史混批时的 padding 计算。

张量准备完成后，对纯时序计算启用 `torch.compile(mode="default")`。CPU/tiny 和缺少相应 API 的环境使用兼容路径；历史速度测量使用 **WSL、PyTorch 2.11.0+cu130、单张 RTX 4090**，不能直接套到其他运行环境。

### 6.2 棋盘编码分块和合并上传

内部棋盘编码块由历史配置的 128 提高到 **2048**，并把索引生成移出分块循环。同一微批的 int16 观察与索引合并上传；one-hot 缓冲使用 autocast 对应精度，参数与 Adam 主状态保留 FP32。

这一步减少大量小分块的 Python 调度、张量分配和 CPU/GPU 传输。块大小需要结合完整历史、优化器状态和训练峰值显存判断，不能只看单次前向能否放入显存。

### 6.3 布阵批量预生成

原本在线环境剩余时间中，相当一部分是 GPU 自回归布阵，而不是 CPU 规则计算。继续增加 CPU worker 无法加速这一部分。

实现一次预生成 **16 局所需布阵**并排队复用，移除每套布局中 25 次已知棋种的 GPU 标量读取。队列保存采样时的对数概率和版本；布阵权重更新后使旧队列失效；检查点保存未使用布局和随机状态。

它把终局换局时的零碎推理摊入批量生成，又避免预取结果与更新后的布阵模型混用。相关逻辑见 [rollout.py](../src/junqi/training/rollout.py) 和 [trainer.py](../src/junqi/training/trainer.py)。

### 6.4 融合优化器、采样 Graph 和低精度残差

启用融合 AdamW，并为形状稳定的采样头捕获 CUDA Graph，减少优化器与采样中的小内核启动。局部实测如下：

| 局部操作 | 原实现 | 优化后 |
|---|---:|---:|
| 实际默认 AdamW 后端 | 4.00 ms | 1.44 ms |
| 采样头 | 0.266 ms | 0.125 ms |

证据见[融合优化器与采样验证](benchmarks/ppo20_fused_sampling_verified_4090_20260911.json)，采样实现见 [ppo_sampling.py](../src/junqi/training/ppo_sampling.py)。这些操作仅占整轮的一部分。

另外使用 BF16 残差减少中间激活与计算开销。历史全参数梯度验证的相对 L2 差异约 **0.60%**，属于有限精度差异；不能宣称位级等价，随机采样后的棋谱也可能分叉。详见[残差验证](benchmarks/ppo20_bf16_residual_validation_4090_20260911.json)和[变长注意力验证](benchmarks/ppo20_varlen_validation_4090_20260911.json)。

## 7. 长历史与 KV：减少重读，同时保留窗口语义

增量推理为每个棋局/席位分配固定 KV 槽位，将该席位上次查询后**已经发生**的多个 token 一起解码；它不预测尚未发生的未来动作。使用 Triton 内核直接读写缓存，并对稳定形状使用 CUDA Graph，终局后释放槽位，权重变化后失效。

后续增加按席位分组的多 query 注意力，共享同一段 K/V 的读取。48 席位、4 query 的局部测试中，1024 extent 约 **1.80 倍**，512 extent 约 **1.40 倍**；短窗口保留原内核。实现见 [fixed_kv.py](../src/junqi/training/fixed_kv.py)、[fixed_kv_kernels.py](../src/junqi/training/fixed_kv_kernels.py)、[grouped_kv_kernel.py](../src/junqi/training/grouped_kv_kernel.py)。

**尚未消除的限制是滑窗边界。** 历史保留初始 token 加最近 1000 个转移。窗口起点移动后，旧窗口不再是新窗口的精确前缀；历史位置和各层表示发生变化，不能简单平移旧 K/V 就声称等价。当前选择精确重建。

| 全窗口诊断场景 | 实测耗时 |
|---|---:|
| 512 个样本、32 条可合并长历史，Policy / Critic 单 epoch | 各约 0.33 秒 |
| 512 个不同滑窗起点、不可合并，Policy / Critic 单 epoch | 2.26 / 2.20 秒 |
| 384 席位，997 → 1001 token 增量解码 | 0.065 秒 |
| 同样 384 席位，滑窗后的精确重建 | 0.823 秒 |

数据见[长窗口容量与数值验证](benchmarks/ppo20_capacity_4090_20260911.json)。历史最快吞吐探针仅约 **0.047%** 的稳态样本达到完整窗口，后期长局比例变化会显著影响工期。

## 8. 试过但没有作为默认采用的方向

| 方案 | 实测发现 | 处理结论 |
|---|---|---|
| 直接把历史 1000 缩到 500 | 独立历史前后向 0.545 → 0.295 秒，但特定跨边界的 512 决策样本由 8 个前缀组变成 512 个，前后向 0.512 → 14.089 秒 | 没有改正式窗口；先解决滑窗复用，再比较完整训练 |
| 对动态 padding 学习器自动捕获 CUDA Graph | 显存压力增大，并出现严重降速 | 保留稳定局部 Graph，学习默认使用 `compile(default)` |
| 固定容量的完整前后向 Graph | 已确认真实 Graph 回放，但局部约 18–21 ms，与现有编译路径接近 | 没有计入额外整轮加速 |
| `max-autotune-no-cudagraphs`、私有 ATen Flash 包装 | 本机验证没有比已有路径带来有意义的额外收益 | 未作为默认运行路径 |
| Policy 与 Critic 分别放入 CUDA stream 同时学习 | 两模型同时更新约 81–96 ms，反而慢于串行 | 未接入默认训练 |

第一项是刻意选择的边界诊断，不代表缩窗后整轮一定慢 27.5 倍。证据分别见[500 步窗口核查](history_window_500_four_dark_zh.md)、[固定 Graph 验证](benchmarks/ppo20_static_graph_verified_4090_20260911.json)、[双 stream 验证](benchmarks/ppo20_stream_profile_4090_20260911.json)和[分项优化报告](ppo20_optimization_zh.md)。

## 9. 下一步仍值得优化的部分

1. **先建立新版完整周期基线。** revision 24 下记录局长、完整窗口占比、前缀合并率、KV 重建次数、各阶段墙钟和显存峰值；覆盖正常布阵更新、评测及保存，避免用短局窗口替代长期分布。
2. **降低学习端成本。** Policy/Critic 学习合计约占上述主要阶段的六成。继续检查输入准备是否重复、形状分组是否降低 padding/重编译、索引和中间激活是否可以减少。以完整轮收益筛选方案，不默认认为更多 Graph 或 stream 更快。
3. **降低 Actor 与未隐藏环境成本。** 测量棋局池、CPU worker 和流水组的组合，查找负载不均、IPC 或重复观察处理。保持每局顺序与独立随机状态，并同时检查 CPU 对弈服务竞争下的吞吐。
4. **重点处理滑窗边界。** 研究批量重建、按窗口起点分组和减少重复编码。若采用分段记忆、位置编码或缓存语义修改，应明确视为模型改动，另做训练与棋力比较，不能宣称与原严格截断窗口等价。

后续方案的验收依据应同时包括：规则和可见信息一致、相同状态的前向/梯度对照、完整优化器工作量、未完棋局与随机状态恢复，以及覆盖长局的完整训练吞吐。棋力需另用冻结检查点、完整规则和公平换座的对战结果判断，不能用 loss 或训练速度替代。
