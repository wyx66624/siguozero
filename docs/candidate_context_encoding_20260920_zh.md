# 删除独立阵亡输入与移动跳过次数（2026-09-20）

后续用户要求删除旧模型并从头训练，已执行 v17 全新初始化；见
[v17 从零训练与完整输入编码](v17_fresh_start_and_encoding_20260920_zh.md)。下文停训记录对应编码修改完成时的状态。

## 结论及证据边界

75 维独立阵亡特征不因为“可以由其他信息推断”就必然干扰训练。显式给出的确定信息可能减轻
网络自行推理的负担；重复特征也可能改变优化和模型依赖的信号，但当前没有消融实验能把
漏防、送子等错误归因于这 75 维。删掉它们是输入设计调整，不能直接等同于棋力提升。

不能只看一枚暗子的 `011` 就认定一名工兵已死：它也可能表示一名工兵已在别处被确认为
`100`。但是，当前编码已从其他候选中排除了已确认存活和确定阵亡占用的槽，因此可以按玩家
对**整盘所有在场棋子的候选槽取并集**，检查哪些类型的槽已经完全不可能在场：

```text
该玩家某棋种的确定阵亡数 = 初始数量 - 该玩家整盘候选并集中该棋种的槽位数
```

例如 `100` 仍在场、其他暗子为 `011` 时，并集为 `111`，确定死亡数为零；`100` 阵亡后，
盘面只剩 `011`，并集有两槽，确定死亡数为一。这里必须先取槽的并集，不能把所有棋子的
多热位直接相加；多个暗子可以同时保留同一候选槽。

用 update 1867 保存的 1536 个动作、6144 个玩家观察做了重建核验：18,432 组玩家库存，
460,800 个阵亡位（其中 50,869 个为 1），全部与原独立阵亡记录一致。因此当前这 75 维
确实有可检验的冗余性，删除输入有合理依据。这不代表网络必然学会并集运算，也不代表删除
比直接给出统计值更容易优化。该验证不声称覆盖全部合法局面。

本次按用户要求删除网络中的独立阵亡输入，继续由规则层维护公开信息，约束后续每枚棋子的
候选槽；没有要求网络重新学习库存扣减，也没有把不确定的暗棋损失替换为裁判真实身份。

## 新的四国输入契约

| 输入 | v16 | v17 |
| --- | --- | --- |
| 棋盘投影输入 | 129 × 26 + 3 + 75 + 4 = 3436 | 129 × 26 + 3 = 3357 |
| 独立确定阵亡网络维度 | 75 | 0 |
| 棋盘内的剩余跳过次数 | 4 | 0 |
| 行动投影输入 | 10 | 14 |
| 行动内的剩余跳过次数 | 0 | 4 |
| 棋盘/行动投影输出 | 384 / 128 | 384 / 128 |

14 维行动输入依次为：起点 x/y、终点 x/y、上一手行动者、无吃子和棋倒计时、
四个相对座位的存活状态、相同座位顺序的剩余跳过次数。每条 token 使用该时刻的计数，
包括尚无前一手动作的初始 token。Actor 和 Critic 均应用此契约，仍保持各自的信息边界。

融合层和 512 维主干保持原样。gamma、lambda、奖励、优势和价值目标算法没有在本次修改中改变。
确定性阵亡规则仍开启。内部历史记录和进程传输仍保存原来的 75 个阵亡字段，以兼容已有记录
及旧模型；它们不参与 v17 的棋盘投影或行动投影，也不通过其他新增支路进入网络。

## 候选扣减规则

当前库存追踪已经实现以下语义，本次保留并回归验证：

1. 初始未知工兵候选为 `111`。确认第一名工兵占用 `100` 后，同一玩家其他尚未确认的棋子
   不再使用该槽，工兵候选变为 `011`。已确认棋子自身保留 `100`。
2. 这名 `100` 工兵阵亡后，其他位置仍为 `011`，不能再扣一次变成 `001`。
3. 若只能确定工兵死亡数量，无法对应一个已分配编号，消耗尚未分配的槽。现有规则从高位
   扣除：没有先前编号时为 `111 → 110 → 100 → 000`。`110` 和 `011` 的差别是占用了哪个
   人工槽号；两者都只剩两个可用工兵名额，不能为追求相同字面图案而重编号已确认的棋子。
4. 工兵、炸弹、地雷及其他重复军阶同样按各自的初始数量处理；观察者和棋子所属玩家分别记账。
   隐藏身份不确定时保留所有公开证据允许的候选。

Critic 使用每枚真实棋子的持久独热槽；阵亡后该棋子从盘面消失，同类存活棋子不重编号。
Actor 对隐藏对手只使用公开确认分配的槽，不读取这些裁判编号。

## 停训与断点边界

训练服务 `siguozero-expand-training.service` 收到正常停止请求，完成 update 1867 后保存断点。
`manifest.json` 的保存原因为 `completed_or_stopped`，累计 183,533,568 环境步。
监控确认 `status=stopped`、`checkpoint_update=1867`、`unsaved_steps=0`、`processes=[]`，
systemd 为 `inactive/dead`、`MainPID=0`。

编码验证结束时，既有 `latest.pt` 保持 v16，未迁移、覆盖或重置。新配置的 v17 第一层参数形状不同，不能直接
续训 v16 检查点。当时保持停训，等待确定后续训练方式；随后用户明确要求删除旧模型并从头训练。
v15/v16 模型仍按自身编码契约读取，便于旧模型推理与对照评测。跨架构历史对手训练池的采用
也不能由“旧模型可以独立推理”推断为已经验证。

## 验证

针对候选编码、独热槽排除、动作编码、Actor/Critic、MAPPO 保存恢复及输入契约的 CPU 联合
测试通过：96 项测试、28 个子场景。覆盖同一已确认工兵存活/阵亡不重复扣槽、初始 token
的跳过次数、四暗/双明、新旧检查点形状检查、列表/数组/前缀合并/滑动 KV 的输出和梯度一致性。

特别验证：候选盘面不变时单独改动历史阵亡位，v17 的网络输出不变；单独改动剩余跳过次数，
棋盘投影不变而行动 token 改变。候选槽本身发生变化时，棋盘投影仍会变化。

全量 CPU 回归为 845 passed、13 skipped、596 subtests passed、4 failed。四项失败均为
旧测试夹具触发 `invalid epoch-completion learning rate settings`；用修改前备份的代码和配置
在独立临时目录重跑，四项均报相同错误。未为本次编码任务改写学习率行为。

真实 v16 / update 1865 推理快照在修改后仍可严格加载：棋盘 3436、行动 10 维，全部合法动作
评分为有限值，能够选择合法动作。原始验证数据及完整报告位于
`output/diagnostics/encoding_change_20260920/`，包括 `current_audit.json`、`pytest_cpu.xml`
和 `baseline_failures.xml`。

测试中的 tiny 模型更新只发生在临时目录，不是恢复正式训练。此处不声称删除 75 维改善了
漏防率、优势符号、收敛速度或棋力；这些需要后续训练和固定条件下的战术/对战对照。
本次没有进行新架构的正式 GPU 训练、CUDA 图性能验证或棋力评测。
