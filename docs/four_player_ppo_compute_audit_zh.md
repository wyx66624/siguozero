# 四国 PPO：参数量、计算放大与性能剖析

预算现按 revision 19 的[总环境交互定义](environment_step_budget_zh.md)，包含实际模拟分支。
本次被测 PPO 没有额外分支，下文“真实动作”的测量数值保持原始含义；网络重算不计环境步。

旧报告里 PRO 6000 约两年、8 卡数月的数字，来自短基准和假定加速比的外推。
它们不能当作硬件能力、训练必要工期或采购依据，相关排期结论现已撤回。
本次查明了当前模型的实际计算放大因素和实现开销；没有测量 PRO 6000、H100 或 CUDA 多卡。
目标保持为单个四国模式 30 亿环境交互步。没有更改模型结构、PPO 超参数或启动正式长训。

## 1. 少量参数可以被重复使用很多次

当前 Policy 144,157,704 参数，Critic 143,698,441 参数，Layout 17,292,288 参数。
Policy 和 Critic 是独立网络。Critic 的输出头只有 513 参数，但它之前的整套骨干仍需计算。

四国每个历史记录不是一个便宜的向量查表：先把 129 个棋盘点加一个汇聚点，
交给 8 层、256 维的棋盘 Transformer，再把汇聚结果与行动表示组合成 512 维历史 token，
送入 32 层时序 Transformer。最多保留初始观察加最近 1,000 次转移。

本次 512 个真实决策样本合并为 11 条前缀序列，当前实现实际编码了 5,330 次历史棋盘，
对应 692,900 个棋盘点 token。原始统计为 `raw_board_tokens=196422`、
`board_input_tokens=board_unique_tokens=board_encoder_tokens=5330`，节约约 97.3%
原本逐样本重复的历史。这是**一个模型、一个学习 epoch 内各 microbatch 的累计编码输入**，
没有把另一个模型、其他 epoch 或激活重算次数计入 5,330，也不是整个训练过程的全局唯一棋盘数。
下面的计算量是在前缀合并优化之后发生的。

512 是参与损失计算的决策位置数，不代表输入只有 512 张当前棋盘。样本的历史平均长
383.64 token、最长 511；相同对局与玩家视角的样本合并后，在最长历史的多个位置读取输出。
例如同一视角训练第 100、104、108 步，合并后编码 `B0…B108` 这 109 个历史状态，
从三个位置取损失，而不是分别编码 101+105+109 次，也不是只编码三个当前状态。
本次 11 条保留序列的历史输入累计为 5,330。

“每个状态编码一次”要区分原始棋盘记录和可训练特征：原始整数记录已由持久历史保存；
神经编码是 `z_t = E_theta(B_t)`，随棋盘编码器参数变化。同一组参数、同一视角和相同输入，
默认零 dropout 下可以共享同一次可微编码；`_encode_full` 已按模式、棋盘码和阵亡先验在
单次前向内去重。该批局部去重没有进一步命中，5,330 是各调用局部去重结果的累加。
跨 microbatch 是否还有重复，需要对全批输入另作全局唯一键统计，不能从这个累计值断定。

采样期缓存的是无梯度推理结果，不能直接作为全历史端到端学习的编码结果：这样会切断
棋盘编码器的历史梯度；之后的 optimizer step 又会使旧参数对应的特征过时。
训练可以在参数不变期间共享保留计算图的特征，但跨独立反向需管理计算图及激活显存，
不能只把推理 KV 缓存开关打开。Policy、Critic 的棋盘编码器参数也各自独立。
[PyTorch 自动求导机制](https://docs.pytorch.org/docs/2.11/notes/autograd.html)、
[detach 的梯度语义](https://docs.pytorch.org/docs/2.11/generated/torch.Tensor.detach.html)

因此，5,330 是当前全历史学习与批次组织产生的工作量，**不是 PPO 必然要求的固定倍率**。
无损优化应继续核查同参数下的跨微批重复、输入整理和重算策略；冻结棋盘编码器、截断历史
梯度或改用历史摘要可以进一步改变成本，但会改变当前训练方式，不能当作无损缓存优化。

| 主模型模块 | 参数量 | 本次 Transformer 主体前向计算占比，含重算 |
|---|---:|---:|
| 棋盘编码器 | 863 万，占主模型约 6% | 约 88% |
| 32 层时序网络 | 1.343 亿 | 约 12% |

占比按实际运行的 block 形状估算矩阵乘法及稠密注意力 FLOPs，非墙钟时间占比，
未包含嵌入、归一化和动作头等其他运算。时序 padding 也计入形状。
因此，单纯砍掉大量时序参数，未必能解决最大的计算瓶颈。

本代码 FFN 为 SwiGLU，有三个矩阵投影；一个 Transformer block 的主要前向计算为：

```text
F(B,S,d,h) ≈ B × (8 S d² + 6 S d h + 4 S² d)
```

乘加按 2 FLOPs 计。棋盘 `S=130,d=256,h=1024`，8 层约为 **2.32 GFLOPs/棋盘**。
这不是每次真实走子的总成本；一次学习会经过许多历史棋盘。

## 2. 两个模型、三轮 PPO 和激活重算继续放大成本

一个真实动作需要策略和价值估计。采集后，策略最多学习 3 轮，价值网络学习 3 轮；
每轮包含前向和反向。为了容纳激活，当前 main 在棋盘和时序网络的每层都启用
activation checkpointing，反向时会重新执行该层前向。
这属于用额外计算换显存的机制。[PyTorch checkpoint 文档](https://docs.pytorch.org/docs/2.14/checkpoint.html)

本次 128 个真实动作的策略前后向，PyTorch profiler 识别出的计算量约为 **12.76 TFLOPs**，
平均约 99.7 GFLOPs/样本/模型/epoch。按两个相近骨干、各 3 轮粗略放大，学习部分就约为
**600 GFLOPs/真实动作**；3B 动作约 `1.8e21 FLOPs`，还未加采样推理、融合注意力等。
这是本批工作量的示例，不是整个训练阶段的固定 FLOPs 预算，也不代表收敛需求。

Profiler 只对部分算子估计 FLOPs，融合注意力等未完整计入，因而上述识别值不是完整计算量。
[PyTorch profiler 文档](https://docs.pytorch.org/docs/2.14/profiler.html)

KV Cache 已用于固定权重下的增量推理。同一轮学习已有精确前缀合并；参数更新之后，
旧缓存不能直接替代新权重的前向和梯度。当前固定初始 token、绝对位置和滑动历史的设计，
在超过 1,000 步后也会破坏原来的精确时序前缀复用，这个阶段仍需单独优化及实测。

## 3. 实现确实还有显著开销

设备为本机 RTX 4090，4 个 PyTorch CPU 线程，BF16 autocast，三个模型及 Adam 状态常驻。
原始记录：[本次计算剖析 JSON](benchmarks/2026-09-10_ppo_compute_profile_4090.json)。

| 同一批 128 个真实决策 | 记录 |
|---|---:|
| 历史平均 / 最大长度 | 371.4 / 509 |
| 合并后的序列 / 历史棋盘数 | 3 / 1,273 |
| 未启用 profiler 的策略前后向 | 0.637 秒 |
| 启用 profiler 的同样操作 | 1.019 秒 |
| GPU kernel、memcpy、memset 事件数 | 23,515 |
| GPU 事件累计执行时间 | 0.453 秒 |
| `aten::mm` 对应 GPU 时间 | 97.45 毫秒 |
| `aten::copy_` 对应 GPU 时间 | 95.72 毫秒 |
| `aten::mul` 对应 GPU 时间 | 46.62 毫秒 |
| CPU `aten::select` 调用数 | 28,937 |

插桩本身增加了约 60% 墙钟时间，不能用 `0.453/1.019` 直接声称真实 GPU 利用率，
也不能把所有非矩阵时间称为可消除的浪费：归一化、激活、注意力和必要搬运仍要执行。
这些数据足以说明，仅用峰值 TFLOPS 比例外推硬件速度会遗漏很多因素。
代码中逐历史记录整理张量、逐行切片再 stack、GPU nonzero 后 tolist、多个小算子的调度，
是值得针对性剖析和向量化的路径。当前已实际使用 efficient attention，不能再把
“打开 FlashAttention”不经测试地算成一笔额外收益。

另一个 512 样本批次，单轮策略前后向 2.433 秒、价值前后向 2.503 秒；这不含 optimizer.step、
采样、保存和评测。它不是端到端每秒步数。

完全关闭重算的 128 样本试验触及约 24 GiB 的本机显存占用，发生严重停滞，已停止该独立进程。
没有得到有效的关闭重算耗时，不能声称关闭后会快多少或 microbatch=8 能完全关闭重算。
大显存设备应实测更大批量及选择性重算；96GB 也不等于任意长序列都能保存全部激活。

### 本次实验边界

- 两轮共 8,192 个真实动作的诊断采集和前后向已完成，历史最长 512，未覆盖长训或窗口滑动。
- 初版诊断脚本把调度总轮数设为 2；两轮仍处于 warmup，JSON 中的实际学习率均为 `1e-6`，
  与生产设置下这两轮的学习率下限一致。文本日志四舍五入后显示 `0.0`，不能据此认为没有更新。
  修订后的工具直接保留生产调度总长度，仅通过真实步数目标限制运行；随机权重和本批零优势不能证明棋力。
- 独立运行禁止自动保存正式检查点；没有修改现有权重或生产训练配置。
- 正式短基准的吞吐证据仍见此前的 `2026-09-10_ppo_sequences_4090.json`，没有用插桩时间更新排期。
- 工具现默认跳过关闭重算压力测试，并把进程 CUDA allocator 限制为显存的 85%，以尽早报告 OOM。
- 修订后的工具已完成一次 8 个真实动作的完整 GPU 冒烟，退出码 0；这个微小样本不参与速度推算。

## 4. 用目标吞吐验收优化，而不是继续猜硬件工期

以下只使用 `时间 = 3B / 完整训练平均吞吐`，吞吐必须包含采集、两个模型优化和保存；
不是单纯推理吞吐，也不是把同一数据训练 3 轮重复计为 3 步。

| 希望完成的时间 | 24 小时连续运行所需吞吐 | 每天 80% 运行所需吞吐 |
|---|---:|---:|
| 30 天 | 1,157 真实步/秒 | 1,447 真实步/秒 |
| 90 天 | 386 真实步/秒 | 482 真实步/秒 |
| 180 天 | 193 真实步/秒 | 241 真实步/秒 |

8 卡如要 90 天连续完成，全机平均需 386 步/秒，即平均每卡贡献约 48.2 步/秒，
通信、负载不均和停顿已经需要反映在实测吞吐里。这是验收要求，不是承诺能够达到。

优化优先级：先向量化输入整理和梯度 gather/scatter、减少小算子启动和同步；
再针对设备显存测试批量、选择性重算以及合适形状下的编译/图捕获；继续处理历史窗口的
重编码和采集阶段调度。改变棋盘编码深度、改为轻量历史表示、共享策略价值骨干等可能进一步
减少计算，但会改变当前模型设计，需要独立的棋力与学习稳定性对照，不能算作无代价提速。

PRO 6000、H100 的单卡吞吐及 2/4/8 卡效率应在上述瓶颈梳理后，以固定真实样本预算、
明确全局 batch 口径和长历史覆盖重新测量。此前人为指定的倍率不能替代这一步。
