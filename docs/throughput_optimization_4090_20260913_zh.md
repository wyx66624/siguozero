# RTX 4090 本轮训练吞吐优化

本轮针对本地四暗棋 PPO。冻结第 1336 轮完整检查点进行独占 GPU 对照，随后从原训练状态恢复。所有探针都使用独立目录，不把探针产生的参数写回正式训练。

## 实际修改

1. **并行棋局从 96 增至 128。** 两组流水的常规推理批量从 48 增至 64，CPU 规则进程仍为 8 个。每轮仍采集 98,304 个真实环境动作，优化器小批仍为 512，Policy 和 Critic 最多各 3 个 epoch。
2. **合并学习输入与同步。** PPO 旧概率、优势、开局标记等标量合并上传；Critic 四类目标合并上传。统计值与梯度范数一次传回 CPU，非有限梯度仍在 Adam 更新前报错。
3. **完整学习前向、损失与反向使用 CUDA Graph。** 每个网络使用 2,560 和 4,096 个历史位置两个容量档位；Policy 另按合法起点数量选择 4,096 / 8,192 / 16,384 档，减少动作评分的填充计算。最多保留六张 Policy 图、两张 Critic 图。有效样本、合法动作和开局熵权重有显式掩码，填充序列独立且不参与损失。超容量或碎片过多的历史走原来的变长注意力路径，合法动作不裁剪。
4. **学习图复用中间计算显存。** 单线程顺序执行，当前梯度经检查并完成 Adam 更新后才执行下一张图。参数、Adam 状态和输入位于共享临时池之外。防止每种形状各自保留整套激活显存。
5. **在线合法动作掩码直接从合法动作构造。** 同时填充起点、终点掩码，减少每个采样波次的 CPU 张量清零、归约和上传准备。
6. **为显存设置预算并回收空闲缓存。** 正式训练与独占探针一致，使用 `ppo.cuda_memory_fraction: 0.90` 限制 PyTorch 分配器。采样每 64 个波次检查一次：仅当保留量超过整卡 85% 且未使用缓存至少 1 GiB 时释放空闲块。活跃 KV、模型和图地址不受影响；释放量记录为 `encoding/fixed_kv_allocator_trimmed_gib`。评测前释放学习图及梯度引用，评测后按需重新捕获。
7. **冷缓存重建按历史长度分组。** 固定 KV 的冷启动原本把一个推理波次补齐到最长历史，少数长局会放大整批临时张量。现在排序后分组，每组填充后至多 8,192 个位置，计算完按原输入顺序写回结果。每条历史完整保留；单条历史超过该预算时独立处理。本地窗口最长 1,001，因此仍在预算内。稳态增量解码仍使用原来的大批量。

本地配置启用 `ppo.learner_cuda_graphs: true`。CPU、NPU、多卡、非 BF16 或不支持变长注意力的配置保留普通学习路径。图的数量和容量固定，没有把训练数据卸载到 CPU 来换取更大的 GPU 批量。

共享图池的前提是图不并发，且旧输出在下一张图执行前已经消费。这与 [PyTorch 2.11 的图显存管理说明](https://docs.pytorch.org/docs/2.11/notes/cuda.html#sharing-memory-across-captures) 一致。这里捕获前向和反向，优化器、梯度异常保护及学习率控制仍在图外。

## 相同工作量对照

全部从同一份第 1336 轮完整检查点恢复，保留模型、Adam、未结束棋局和 RNG。每个 3 轮实验均为 **294,912 环境动作、1,728 次 Policy 更新、1,728 次 Critic 更新、3 次布局更新**。仅在探针中关闭 KL 提前退出，使优化次数严格一致；正式训练保留原有 KL 保护。

| 配置 | 首轮，含编译/捕获 | 后两轮均值 | 最高 PyTorch 保留显存 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 原代码，96 局 | 104.75 秒 | 85.00 秒 | 15.59 GiB | 基线 |
| 原代码，128 局 | 103.81 秒 | 83.93 秒 | 20.35 GiB | 只扩池收益约 1.3% |
| 96 局，单档学习图 | 83.36 秒 | 71.15 秒 | 18.28 GiB | 学习阶段加速 |
| 96 局，两档独立图池 | 84.89 秒 | 67.51 秒 | 20.31 GiB | 填充计算减少 |
| 112 局，两档独立图池 | 85.73 秒 | 72.04 秒 | 21.55 GiB | 第二轮缩批到 28，未采用 |
| 128 局，两档独立图池 | 86.23 秒 | 未完成 | — | 第二轮 KV 分配超过探针 90% 显存上限，未采用 |
| 128 局，两档共享图池 | 84.53 秒 | 65.47 秒 | 20.73 GiB | 三轮保持推理上限 128；后续正式运行暴露问题，见下文 |
| 128 局，再按合法起点分档 | 85.31 秒 | 61.60 秒 | 21.00 GiB | 三轮无缩批 |
| **128 局，分档并限制冷缓存重建批量** | **79.31 秒** | **60.62 秒** | **20.14 GiB** | **最终采用，三轮无缩批** |

最终方案的持续轮吞吐相对原 96 局基线提升约 **40.2%**，耗时减少约 **28.7%**。三轮连同初始化共 **200.88 秒**，同口径吞吐提升约 **37.0%**。短探针中初始化成本占比高，不能混用冷启动和持续轮两个口径。最高 PyTorch 实际分配量约 **17.95 GiB**。

最后增加合法掩码优化后，再验证了 2 个完整轮：85.55、65.45 秒，共 196,608 动作、Policy/Critic 各 1,152 次更新。此项的额外收益没有超过实验波动，不单独声称加速百分比。

新增棋局会改变采样轨迹；后续轮还会因 BF16 数值差异产生不同轨迹。严格相同的是起始完整断点、真实动作数和优化器工作量，不是每个动作的随机结果。探针包含采样、学习、布局更新、图捕获和轮内日志；不包含正式评测与模型保存。

冷缓存分组会改变 BF16 矩阵计算的批形状，所以此版本从首轮就可能产生不同轨迹。对局长度与每轮可用布局样本量也会有变化；原始记录同时保留这些量，不能把它们说成完全相同的张量输入。

## 正确性与恢复

- CPU FP32 对照验证了填充掩码、强制单动作、分阶段熵、Policy/Critic 损失与梯度；保留冻结席位不参与 Policy 更新的原有处理。
- RTX 4090 BF16 对照覆盖 512/243 样本、两种容量与两个网络交错回放。梯度相对 L2 差异最高约 2.25%，属于本次记录的数值误差，**不是逐位相同**。单步参数差异最高约 4e-5，近零梯度的 Adam 更新可能放大符号差异；这些测试不证明棋力完全相同。
- 另测三个完整 1,001 token 历史窗口，包含同一局连续滑窗起点。各窗口独立，未连接不同起点；BF16 梯度相对 L2 差异低于 1%。
- 最终动作起点分档另有 12 组 GPU 验证，覆盖 128/243/512 样本、三个起点档位与交错回放；梯度相对 L2 差异最高约 1.80%。
- 冷缓存验证在 RTX 4090 上预留 512 个席位，比较 64 条不同长度的历史，并再次比较追加动作和完整滑窗后的结果。与完整注意力参考相比，context 相对 L2 差异约 0.84%～0.86%，最大绝对差约 0.052；重复读取缓存逐位相同。最长窗口仍为 1,001，每组填充量不超过 8,192。该探针不包含常驻学习图，不能作为正式训练显存峰值。
- 注入 NaN 后，回放产生的异常梯度在 Adam 前被拒绝，参数和 Adam 步数不变。
- 扩池必须显式传 `--expand-game-pool`，只允许单卡增大，不允许缩小并丢弃未结束棋局。原棋局、布局队列、RNG、模型和优化器均保留。正式采样前保存扩容后的完整断点，后续普通重启即可恢复。

回归验证：最终版本完成 406 项 Python 测试，其中 398 项通过、8 项因环境条件跳过；33 项页面测试全部通过。旧学习率测试中的简化夹具未绑定拆分后的调度方法，已改用真实 Trainer 方法并通过完整复测。

正式配置保留当前的模型、规则、1,001 token 窗口、熵目标、学习率上下限、KL 保护和历史席位比例。当前本地评测配置已经是 **500 局 / 5,000 万步**，完整续训断点为 **2,500 万步**；本轮性能优化没有调整评测日程。

## 工期口径

最终进程从第 1345 轮恢复。剔除启动编译和 CPU 回归测试占用的前两轮后，使用第 1347 轮结束到第 1359 轮结束之间的 **12 个完整周期**：

| 项目 | 观测值 |
| --- | ---: |
| 真实环境动作 / 墙钟时间 | 1,179,648 / 669.75 秒 |
| 完整周期平均耗时 | 55.81 秒 / 轮 |
| 完整周期吞吐 | **1,761.33 步 / 秒** |
| 每轮 Policy / Critic 更新次数均值 | 293.83 / 576 |
| 在线采样 / Policy 学习 / Critic 学习 / 布局学习均值 | 32.97 / 8.25 / 10.02 / 2.73 秒 |
| 推理批量 | 全部保持 128 |
| 每轮记录的最大已分配显存 | 17.97 GiB |
| 45 次资源采样中，最大保留显存 / 整卡占用 | 19.62 GiB / 21,775 MiB |

这个窗口包含第 1350 和 1355 轮的网页模型快照，以及例行日志和轮间开销；未遇到正式评测与完整检查点保存。资源轮询峰值只是观测值，不是连续显存追踪。截至窗口末尾已完成 14 轮，该窗口不包含前两轮；没有复现停滞或 OOM 缩批，仍不能替代多日稳定性验证。

第 1359 轮后还剩 **2,866,404,864** 环境步。按当前速度，训练本体条件外推 **18.84 天**。加上下文中的现行评测成本，再为约 115 次完整保存预留约 0.03 天，合计约 **20.0～20.3 天**。已接近目标，尚不能确认 20 天以内。

正式 PPO 仍按 KL 提前结束策略更新，因此这里平均约 1.53 个 Policy epoch。若后续大多数轮都完成全部 3 个 epoch，用本轮固定工作量探针的 60.62 秒再外推，加同样评测与保存成本约 **21.7～21.9 天**；这也没有覆盖更多长局滑窗的成本。不能用当前早停比例保证全程工期。

### 正式运行中发现的显存问题

首个正式进程未设置探针已有的 90% 分配预算。它完成两轮后，在第三轮采样的 CUDA 流同步处停滞：整卡约 23,563 MiB / 24,564 MiB，GPU 利用率 100%，显存控制器利用率 0%，功耗约 113 W。GDB 堆栈定位到 CPU 拷贝等待 CUDA 同步；没有 CUDA 错误回溯，因此**不能据此确定是换页、驱动还是内核问题**。

正常停止信号无法被主线程处理，最终仅终止该训练进程组，从已保存的第 1336 轮完整断点恢复。第 1337、1338 两轮未保存参数，需要重算。扩容后的棋局池已提前完整保存，恢复仍为 128 局，原未结束棋局没有被丢弃。

上述显存预算与空闲缓存回收随后加入正式路径，再观察持续运行。短探针成功不等于已经验证多日稳定性；初次停滞的两轮不能用于宣称已经达到目标工期。

第二个正式进程完成至第 1345 轮并正常保存；第 1343 轮曾因 OOM 把推理批量从 128 降至 32。这促成了后续合法起点分档和冷缓存分组。最终恢复使用显式 `--reset-oom-batch-limits` 重新尝试配置中的批量；普通恢复仍尊重检查点中的 OOM 限制，其他训练状态不变。

已存在的旧评测记录中，100 局用时 350.56～407.05 秒。按同样每局成本线性估算，500 局约 29～34 分钟；从当前进度到 30 亿步还剩 58 个现行评测门槛，合计约 **1.18～1.37 天**。这只是旧评测成本的条件估算，新的历史对手/队友组合可能改变成本。

若按之前提出的半程后每 2,500 万步评测，而非当前配置的 5,000 万步，还要多约 30 轮，按同一旧成本再加约 **0.61～0.71 天**。本轮未通过减少评测来取得吞吐收益。

后半程历史角色混合、长局滑窗比例、评测局长、完整断点保存和停机均可能拉长工期。当前阶段达到某个条件 ETA，不等于已经证明整个剩余训练能在该天数内完成。
