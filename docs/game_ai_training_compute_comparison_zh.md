# 四国军棋、斗地主和围棋：参数量为什么不能直接换算训练时间

> revision 20 已改为[整盘向量单层投影](whole_board_linear_zh.md)。本文的逐点图编码器、旧参数量和已有性能数字属于修改前版本，不能作为新架构的计时或显存结论。

本次只分析现有代码、计时记录和原始论文，没有改动网络或启动正式训练。
结论是：**一亿参数不意味着必须训练几年；当前成本来自网络如何处理历史、两套独立骨干、
重复学习、30 亿交互目标和实际执行效率。** 当前架构是否值得付出这些计算，仍需棋力对照。

## 1. 参数是权重数量，FLOPs 是这些权重被使用的次数

一个 `256 × 256` 的权重矩阵只有 65,536 个参数，但对 1000 个位置分别做矩阵乘法，
就需要约 `2 × 65,536 × 1000 = 131,072,000` 次浮点运算。
参数不增加，计算却随着输入位置数增长。本文一次乘加计 2 FLOPs。

因此应看：

```text
总时间 = 采样时间 + 网络学习时间 + 环境/调度/数据搬运 + 保存 + 评测
网络学习量 ≈ 每次前向成本 × 实际输入位置数 × 学习次数 × 反向及重算系数
```

这个式子是成本分解，不是用参数量预测工期的精确公式；注意力还受序列长度影响。

## 2. 本项目实际训练的内容

从当前 `ModelConfig.main()` 在 PyTorch meta 设备上重新计数：

| 模型 | 参数 |
| --- | ---: |
| Policy | 144,157,704 |
| Critic | 143,698,441 |
| Layout | 17,292,288 |
| 三个可训练模型合计 | 305,148,433 |

Policy 与 Critic 的骨干各自训练；Critic 虽然最后只输出一个数，前面的网络仍要完整运行。
另有冻结的 Layout reference，占用内存但不属于上表可训练参数。

每个历史记录的棋盘编码：130 个 token（129 棋盘点及一个汇聚点）、8 层 Transformer、
宽度 256、SwiGLU 中间宽度 1024。棋盘摘要与动作信息组成时序输入，再通过 32 层、
宽度 512 的历史网络；最多保留初始观察及 1000 次转移。

一个 block 的主要前向矩阵和稠密注意力计算近似为：

```text
F(B,S,d,h) = B × (8 S d² + 6 S d h + 4 S² d)
```

由此棋盘编码的 8 层约为 **2.319 GFLOPs/棋盘/前向**。嵌入、归一化和动作头未全部包含。

此前实测 512 个决策样本，已做历史前缀合并，仍在单模型、单个学习 epoch 中编码
5330 次棋盘，即 692,900 个棋盘点 token，棋盘部分单次前向就约 **12.36 TFLOPs**。
这不是 5330 个环境动作；它是训练网络读入的历史状态数，各微批次累计。
历史输入、另一个模型、多轮学习和 activation checkpointing 的重算是不同的成本来源。
KV Cache 已用于冻结权重的采样阶段；其无梯度结果不能直接替代更新参数后的历史反传。

这一批的 block 插桩中，棋盘编码占主体前向及重算计算的 **87.9%**，
但它仅有 863 万参数，占 Policy 参数约 6%。这是 FLOPs 占比，不是墙钟占比。
所以仅减少 32 层历史网络的参数，不一定消除最大的计算来源。
原始证据：[计算剖析](benchmarks/2026-09-10_ppo_compute_profile_4090.json)，
[计算口径和性能审计](four_player_ppo_compute_audit_zh.md)。

## 3. 30 亿步对应多大的学习工作量

同一审计中的 128 样本子批，profiler 识别到 **12.758 万亿 FLOPs**，
相当于约 99.67 GFLOPs/决策样本/模型/epoch。融合注意力等未完整计入。
若按两个相近骨干各跑 3 轮估算：

```text
每个环境动作对应学习量 ≈ 99.67 GFLOPs × 2 × 3 ≈ 598 GFLOPs
30 亿动作的示例学习量 ≈ 598 × 10^9 × 3 × 10^9 ≈ 1.79 × 10^21 FLOPs
```

这是短历史子批的数量级示例，不能宣称是整段训练固定预算或下界；
不同局长、前缀复用、微批次、KL 提前停止都会改变每步成本。
采样推理、完整的算子成本、布阵、保存和选拔也未全部包含在这个放大式里。

另一个有用的口径：30 亿动作，若 Policy/Critic 都跑足 3 个 epoch，
总共是 **180 亿次决策样本呈现**，每次还包含该样本需要的历史。
这些重复学习不增加 30 亿环境交互计数。

已有四暗完整两轮短计时为 10240 个环境动作、含逐轮保存约 331.6 秒，即 30.88 步/秒。
`30 亿 / 30.88` 得到约 1125 个连续运行日。这个换算只说明沿用该吞吐跑满预算的时间，
不说明必须学习这些天才能具备棋力，也没有覆盖成熟策略或长历史窗口。
原始证据：[完整短计时](benchmarks/2026-09-11_ppo_eta_four_dark_4090.json)。

## 4. 与论文模型对照

下表比较已公开的代表系统，不把“达到某个基准”的时间与“完整实验训练时间”混用。
围棋参数为按论文网络层形状估算的数量级，**不是作者公布的精确参数总数**。

| 系统 | 网络参数量 | 训练硬件和论文时间 |
| --- | --- | --- |
| DouZero，2021 | 地主 1,457,665；每个农民 1,514,497；三角色共 4,486,659 | 48 个 CPU 处理器、4 张 GTX 1080 Ti；2 天超过监督基线，完整实验训练 30 天。3 张 GPU 采样、1 张学习。[论文](https://proceedings.mlr.press/v139/zha21a/zha21a.pdf)、[官方模型代码](https://raw.githubusercontent.com/kwai/DouZero/main/douzero/dmc/models.py) |
| AlphaGo Zero，20-block，2017 | 约 2300 万，共享 Policy/Value 骨干 | 3 天、490 万盘自对弈；网络优化用 64 个 GPU worker、19 个 CPU 参数服务器，另有自对弈系统。[原论文](https://dsbrown1331.github.io/advanced-ai/readings/alphaGoZero.pdf) |
| AlphaGo Zero，40-block，2017 | 约 4600 万，共享骨干 | 40 天、2900 万盘自对弈；同一论文描述上述分布式优化系统。[原论文](https://dsbrown1331.github.io/advanced-ai/readings/alphaGoZero.pdf) |
| AlphaZero 围棋，Science 2018 | 约 2300 万，共享骨干 | 13 天；5000 个第一代 TPU 生成自对弈，16 个第二代 TPU 学习。[官方论文](https://storage.googleapis.com/deepmind-media/DeepMind.com/Blog/alphazero-shedding-new-light-on-chess-shogi-and-go/alphazero_preprint.pdf) |

DouZero 的计数按公开代码的 LSTM(162,128)、五个 512 宽隐藏层及标量输出复算，
只计算三个角色的逻辑网络，不把 actor 中复制的权重重复当成模型参数。
它用完整轨迹回报拟合 Q 值，不需要像本项目以前的 GRPO 一样每个根局面生成 8 条分支。

围棋参数估算采用 17 个输入通道、256 通道主干、初始卷积加 19 或 39 个残差块，
以及共享主干后的两个头；卷积不带 bias、BN 有可训练仿射参数、全连接有 bias。
按这些假设得到约 2283 万/4644 万；不同 bias 实现不会改变表中的量级结论。

“4 个 TPU”是围棋论文中用于对战的一台程序的配置，不能据此把整套训练说成 4 个 TPU。
AlphaZero 此处使用 **2018 Science 版本**的时间及硬件；不混用 2017 预印本中的 64 个训练 TPU。
2018 论文的 Go 实验共 1.4 亿盘，每次搜索 800 次模拟；70 万次优化更新、每批 4096 个局面，
即 28.672 亿次训练局面呈现。这些分别是盘数、搜索次数和优化样本数，均不等于本项目的环境步计数。

## 5. 对本项目意味着什么

计算多是可以解释的，但不能据此证明当前设计合理，或军棋必须比这些游戏训练得更久。
目前尚无棋力证据证明 1.44 亿 Policy、独立同规模 Critic、32 层长历史都是必要的。
合理的下一步是用现有固定对手评测比较更轻量的棋盘编码、共享 Policy/Value 主干、
更紧凑的历史表示，以及当前模型；以达到相同棋力所用的墙钟时间和资源判断。
这些会改变模型设计，不能承诺无损提速。

同时仍有工程优化空间：现有 profiler 记录了大量小算子、历史张量整理和搬运；
数学 FLOPs 不能直接除以显卡宣传的峰值算力得到工期。已经运行的 KV 缓存、前缀合并
不能重复算成未来收益；也不能承诺换成更大显存就自动消除这些开销。
