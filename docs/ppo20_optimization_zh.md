# RTX 4090：20 天目标的分项优化与完整训练复测

目标为四暗 main 模型的 **3,000,000,000 次真实环境动作**，单张 RTX 4090。
20 天连续运行要求达到 **1,736.11 动作/秒**。网络前后向、Critic bootstrap 和重复 epoch 不增加环境动作计数。

本轮已经实现四类优化，并用独立诊断进程读取四暗检查点复测。没有恢复暂停的正式训练，也没有覆盖原模型。
目前通过完整优化器步数审计的 96 局、大采样轮次试验约 **1,273.13 动作/秒，27.27 天连续训练**，目标尚未达到。
保留 48 局及原采样规模的默认兼容配置为 **33.54 天**。不能将局部加速倍数相乘作为整轮结果。

| 配置 | 完整测量轮次 | 稳态 30 亿步连续天数 | 80% 可用时间下的日历天数 |
|---|---:|---:|---:|
| 上一轮 48 局版本，同一统计方法 | 12 | 71.46 | 89.33 |
| 本轮默认兼容配置，48 × 256 动作/轮 | 12 | 33.54 | 41.92 |
| 本轮吞吐配置，96 × 1024 动作/轮 | 8 | 27.27 | 34.09 |

吞吐配置距离 20 天还需要 **1.364 倍**整体速度。原约 70 天的报告包含启动轮；本表统一排除前两轮估计稳态，再把启动超额耗时计入一次，所以基线数字略有差异。
机器可读审计与逐轮耗时在[最终 ETA](benchmarks/ppo20_final_eta_20260911.json)。

## 已实现的四部分

| 部分 | 实现 | 正确性边界 |
|---|---|---|
| 棋盘编码与上传 | 编码分块 2048；索引移出分块循环；整个微批的 int16 观察和索引合并上传；one-hot 缓冲跟随 autocast 精度 | 参数与 Adam 主状态保持 FP32；0/1 特征本身不损失精度 |
| 批量布阵 | 一次预生成 16 局所需布阵；缓存未使用结果；移除 25 次已知棋种的 GPU 标量读取 | 队列包含原采样对数概率与版本；权重变化后失效；检查点保存未使用布阵和 RNG |
| 学习端与在线流水 | 张量化历史准备；变长 Flash Attention 去掉 padding；`torch.compile(default)`；融合 AdamW；采样头 CUDA Graph；Critic 在采样结束后批量计算；两个独立游戏组交错执行 GPU 推理与 CPU 规则推进 | Policy 在整轮采样中冻结；Critic 用未更新权重计算每个原状态与 bootstrap 的值；GAE、奖励、PPO clipping 保留 |
| 长历史与 KV | 合并相同历史前缀；固定席位缓存多 token 一起解码；Triton 同时处理一个席位的多个 query，复用 K/V 读取 | 初始 token 加最近 1000 个转移保留；窗口起点变化时精确重建；不跨参数更新复用旧 K/V |

CPU 环境还直接生成数值观察，避免为每个座位反复建立 `ObservedPiece`、`ObservedEvent` 和 `StateTokenRecord`。
它调用规则引擎原有的身份可见性判断；已针对二人、四暗、双明及死规则开关逐步对照公开观察。

## 局部证据与不采用的方案

- [变长注意力前向、全部梯度验证](benchmarks/ppo20_varlen_validation_4090_20260911.json)：覆盖短历史、1001 token 和不同滑窗起点。
- [BF16 残差验证](benchmarks/ppo20_bf16_residual_validation_4090_20260911.json)：全参数梯度相对 L2 差异约 0.60%；这是有限精度验证，不代表位级一致或棋力验证。
- [多 query KV 内核](benchmarks/ppo20_grouped_kv_4090_20260911.json)：48 席位、4 query、1024 extent 的局部内核约 1.80 倍；512 extent 约 1.40 倍。短窗口保留原内核。
- [融合 AdamW 与采样 Graph](benchmarks/ppo20_fused_sampling_verified_4090_20260911.json)：实际默认 AdamW 后端约 4.00 ms → 1.44 ms；采样头约 0.266 ms → 0.125 ms。它们只占整轮的一部分。
- 全学习器对动态 padding 形状自动捕获 CUDA Graph 曾导致显存压力和严重降速，该配置不作为默认。
- `max-autotune-no-cudagraphs` 在本机的验证没有快于 `default`；直接包装私有 ATen Flash 接口也未出现有意义的额外收益，未接入运行路径。
- [固定容量 Graph 的实际回放验证](benchmarks/ppo20_static_graph_verified_4090_20260911.json)确认前向和反向各一次 `cudaGraphLaunch`，但约 18–21 ms 的局部结果与现有编译路径接近，不将其计为额外整轮加速。
- [独立 Policy/Critic 双 stream 试验](benchmarks/ppo20_stream_profile_4090_20260911.json)通过同批参数与 Adam 状态对照，但两个网络同时更新约需 81–96 ms，慢于串行，未接入默认训练。

## 时间如何核算

统一使用 `tools/report_ppo20_eta.py`：预先约定前两轮为启动阶段，后续**所有**完整轮次用于稳态吞吐，期间晚出现的编译或长局波动仍计入。
首次启动超额耗时只计一次。每轮逐项核对实际 Policy、Critic 优化器次数，确认均完成 3 epoch、每次 512 个监督样本。

96 局 × 1024 动作的试验将一轮采样量扩大到 98,304，同时将每条学习前缀的样本上限提高到 256。
它改变了采样轮次和小批次组成，不能称为与旧版本逐样本轨迹相同。
warmup / 布阵更新 / reference 更新按原来的环境动作数量对应到 250 / 1 / 6250 轮。
模型结构、总环境动作数、优化器样本数、每样本 epoch、历史窗口均保留。

吞吐配置按每 12,288 个环境动作归一化，Policy 学习约 2.96 秒，Critic 学习约 2.61 秒，在线采样约 3.77 秒。
其中在线采样包含约 2.13 秒 Actor 推理和约 1.27 秒未被流水重叠隐藏的环境处理；这些子项已经包含在采样总时间里，不能再相加一次。
剩余开销主要在两个 32 层小宽度网络的学习、逐动作 Actor 推理、规则及历史维护；布阵已不再是先前那样的主瓶颈。
即使假设剩余环境处理时间完全消失、其余阶段耗时保持当前水平，总时间也仍约 23.7 天。因此继续增加 CPU 进程不能单独解决 20 天目标。

## 长历史验证与时间风险

[全窗口容量与数值验证](benchmarks/ppo20_capacity_4090_20260911.json)保留三个模型的 Adam 状态和布阵参考模型，使用 main 模型与 32 学习微批：

| 场景 | 实测耗时 |
|---|---:|
| 512 个样本、32 条可合并的长历史，Policy / Critic 单 epoch | 各约 0.33 秒 |
| 512 个不同滑窗起点、不能合并，Policy / Critic 单 epoch | 2.26 / 2.20 秒 |
| 384 个席位，从 997 token 增量解码至 1001 | 0.065 秒 |
| 同样 384 个席位，窗口移动后精确重建 | 0.823 秒 |

本次容量压力测试峰值 reserved 约 14.82 GiB；完整吞吐测量的峰值约 16.34 GiB。
增量与重建后的完整动作 log-probability 同全前向对照，最大绝对差异分别约 0.00448 和 0.00421，处于本次 BF16 验证容差内。

吞吐配置的稳态测量仅有约 0.047% 的样本到达完整窗口。用上表的合成压力成本作敏感度估算，
**无法合并的长窗样本每额外增加 1 个百分点，仅学习端就可能增加约 9 天**；这不是实际后期预测，且未包括 Actor 重建增加的成本。
因此不能把 27.27 天理解为完整长期训练的保证时间。保持现在的“窗口移动后精确重算”语义，是后期工期的关键约束。

## 最终配置与使用

[默认配置](../configs/bootstrap.yaml)保留 48 局、每轮 12,288 个动作和原有调度周期，启用本轮经过验证的执行优化，兼容原池大小的检查点。
`scripts/start_four_player_ppo.sh` 继续读取该配置。

[4090 吞吐配置](../configs/ppo_4090_throughput.yaml)是完整、可单独加载的配置快照，针对**新运行目录**使用 96 局、8 个规则进程、两组流水及每轮 98,304 个动作。
不能将旧 48 局检查点直接当作 96 局池精确恢复；测速工具仅在隔离内存中保留旧局并补充新局。

```bash
PYTHONPATH=src python -m junqi.training.train_four_dark \
  --config configs/ppo_4090_throughput.yaml --model-scale main \
  --device cuda --run-dir runs_four_dark_ppo20
```

本轮没有执行上面的正式训练命令。测量环境使用 PyTorch 2.11.0+cu130；项目新增 `training-cuda` 安装选项，对应 PyTorch 2.11.0。
原 `training` 选项继续保留 2.7.1。缺少公开 varlen API 的旧版本会回退到张量化 causal SDPA，其速度不适用本页 2.11 测量。
CPU/tiny 不编译；关闭数组历史、选择一个环境 worker 或关闭延后 Critic 时，可以使用兼容的非分组采集路径。

所有天数都是该检查点与所测历史分布下的条件外推。评测、保存、停机需要另计；后期长局更频繁时，滑窗重建会使时间上升。
`6ND` 给出的稠密语言模型 FLOPs 等价量，不能直接当作在线自博弈端到端时间。

  该分布式验证使用 CPU/Gloo，不是多 GPU 吞吐测量。

每次完整测速恢复模型、Adam、未完棋局和 RNG；额外棋局在计时前生成。正式检查点的修改时间和文件大小保持不变。

带 `candidate_validation_error` 或 `complete: false` 的试验不参与最终 ETA。
其中一次 512 动作/局探索完成训练后在报告序列化遇到 Path 类型错误，已修复测速工具，保留失败标记，不将其包装为正式通过的数据。

这些检查证明限定输入下的规则、数值与吞吐行为；没有进行新模型长期训练或冻结检查点棋力对战，不能据此声称棋力提升。

PyTorch 的 [torch.compile 文档](https://docs.pytorch.org/docs/2.11/generated/torch.compile.html)说明不同编译模式及 CUDA Graph 的内存取舍；本页的速度判断以仓库内完整训练实测为准。
