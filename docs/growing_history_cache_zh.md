# 增长历史训练库与内存缓存

2026-09-13，适用本地 RTX 4090、四暗 PPO、30 亿环境步预算。

## 行为与范围

从 6 亿步起，所有完整训练检查点的冻结 Policy/Layout 都加入训练库；原来的少量早期快照保留。从 15 亿步起，按新开局数使用独立的 20% 历史对手、20% 历史队友，交集目标 4%。同一驻留批次的历史席位共用一个冻结版本，1024 个混合新开局后等待旧局结束再换。

全部有效版本保留非零抽样概率。最终分布一半用于挑战程度，一半用于训练阶段覆盖。阶段按总进度每 10% 划档，对已有版本的档均分覆盖概率，再在档内均分；避免大量相邻 checkpoint 挤掉较早的合作习惯。这是项目的工程选择，不是论文证明的最优比例。

训练库与独立评测分开。当前配置全程每 5000 万步评测 500 局，保留完整四局换位组和一半历史队友，始终挑战历史冠军；总得分率超过 50% 才替换冠军，15 亿步后沿用同一规则。训练继续使用最新参数。前半程收集的早期版本仍保留在历史库，500 局不会平均分给全部训练版本。具体协议见[全程历史冠军挑战赛](historical_opponents_zh.md#全程历史冠军挑战赛)。对指定对手的表现不能代替额外的未参与训练队友与对手泛化验证。

## 减少搬运

| 位置 | 保存内容 | 上限和行为 |
|---|---|---|
| 磁盘 | 不可变的原精度 Policy/Layout；哈希、步数、版本信息 | 保留所有入库版本，不保留历史 Critic/优化器 |
| RAM | 已完成线性层 AMP 转换的连续权重块 | 每 rank 上限 32 GiB，动态保留 16 GiB 可用内存，LRU 回收 |
| 锁页 RAM | 下一批实际选中的版本 | 一份、上限 256 MiB；复制完成前不释放 |
| GPU | 当前历史版本的 Policy/Layout | 一份、复用原存储；KV 与既有采样容量共享 |

一个后台线程在当前批次收尾和学习阶段读取、转换下一版本。新入库模型直接由已经下载的 CPU 权重填入缓存；完整检查点也复用同一份原精度 CPU 权重，避免重复下载。原精度快照与优化器恢复不受 BF16 推理缓存影响。

GPU 传输按 dtype 合并提交，只在整组复制结束后等待一次。锁页内存只用于少量传输缓冲；给整个 32 GiB 缓存锁页会限制系统回收能力。复制完成前保留来源的做法遵循 [PyTorch 的 pinned memory / non_blocking 指南](https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html)。

缓存是可丢弃的加速层。停止后恢复仍读取完整 latest.pt；历史 ID、下一批预选 ID、概率、抽样时库大小、随机状态和未结束棋局均恢复。重新读盘只影响启动后的冷加载速度，不改变抽样和学习归属。内存不足自动回收；锁页失败回退普通内存。

## 四个真实模型的切换对照

使用 update 1503、1370、1345、1336 四个真实完整检查点，生产训练在完整保存后暂停，GPU 独占。每条路径执行 16 次版本加载，首次四次与后续热切换分别记录。来源路径和 SHA-256 见[原始结果](benchmarks/historical_cache_4090_20260913.json)。

| 路径 | 后续切换中位数 |
|---|---:|
| 每次重新读取、CPU 转换并上传 | 403.5 ms |
| RAM 命中，现场准备锁页缓冲并上传 | 36.7 ms |
| 后台已完成预取，切换时上传 | 23.9 ms |

预取准备本身的中位耗时约 13.1 ms，已独立记录，没有作为免费工作隐藏。首次加载包括模型构造、文件校验等，未混入热切换中位数。对每个模型、同一组合法观察，三条路径的 CUDA BF16 输出逐项精确一致；GPU 权重存储地址在切换间保持不变。每版本上传约 **142,460,162 字节**，四个版本的 RAM 数据合计 **569,840,648 字节**，后续 12 次切换不再读取权重文件。

约 241 个同规模版本的准备后权重为 32 GiB 左右，接近缓存上限；加上更早版本或额外停止保存时，少数版本会按 LRU 回收。磁盘上的原精度推理快照约需 52 GB，另加早期和额外节点。缓存量增长不会增加每步执行的模型数量。

这是切换环节约 17 倍的局部收益。正常训练每一大批混合棋局才换一次历史版本，不能把该倍数当作整轮训练加速，也不能据此承诺 20 天完成。

## 完整 PPO 对照与验证

另从同一个 update 1503 检查点，在独立诊断目录将环境进度置于半程门槛，分别关闭和开启 RAM 缓存。每组 3 个更新、294,912 个真实环境动作；固定完整 PPO epochs，比较相同优化器工作量。为了在有限诊断中发生切换，历史 cohort 设为 64 个混合新局；生产配置仍为 1024。此探针不保存模型参数、不修改生产计数，且不包含周期评测和完整检查点保存时间。

结果分别写入[无缓存对照](benchmarks/historical_mixed_cache_0_4090_20260913.json)和[32 GiB 缓存对照](benchmarks/historical_mixed_cache_32_4090_20260913.json)。单次短窗对照只用来检查是否引入明显开销；不能替代整个后半程、不同种子、长滑窗和正式评测成本的长期观察。

| 同一模型和相同工作量的短窗 | 无 RAM 缓存 | 32 GiB 缓存 |
|---|---:|---:|
| 环境步 | 294,912 | 294,912 |
| Policy / Critic / Layout Adam 步数 | 1,728 / 1,728 / 3 | 1,728 / 1,728 / 3 |
| 总墙钟 | 221.07 s | 217.88 s |
| 整轮吞吐 | 1,334 步/s | 1,354 步/s |

这一次差异约 1.5%，不能作为稳定的整体提速承诺。两组学习后的具体轨迹有差异，GPU BF16 训练不是位级确定的，后两轮平均历史长度也略有不同；固定模型的加载路径数值一致性已在独立探针精确验证。这里固定了完整 epochs，因此吞吐不可直接当作启用 KL 早停的正式训练 ETA。

另用真实全精度模型单独测得[历史快照写盘](benchmarks/historical_archive_4090_20260913.json) **1.128 秒**，额外 GPU 分配峰值 **145,310,208 字节（约 139 MiB）**，返回的 CPU 权重与原始完整检查点逐项精确一致。此测量包含新增历史快照及 RAM 准备，未把完整优化器检查点的原有写盘时间算成新增开销。以 1000 万步一次计，它不会按库模型数反复上传全库权重。

测试覆盖：从 20% 起完整检查点入库、同更新去重、数百版本不扩大固定评测预算、阶段抽样覆盖、库增长时的重要性校正、缓存容量不改变 RNG/调度、预选版本断点恢复、RAM 命中不再转换/读盘、内存压力回收、坏文件检测、真实混合 PPO 更新和优化器完整恢复。监控页面展示训练库/评测库数量、缓存容量与命中、读盘次数、锁页缓冲及切换等待。
