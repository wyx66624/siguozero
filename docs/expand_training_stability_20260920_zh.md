# Expand 训练波动与采样流水线优化

记录日期：2026-09-20 至 2026-09-21。对象为 `runs_expand_mappo/four_dark/with_dead_rules`，RTX 4090，配置 revision 33。正式训练与隔离诊断不同时使用 GPU。

## 已核实的原因

训练速度的下降包含不同现象，不能只用一项 GPU 利用率解释。

1. **每个动作的计算量随对局变化。** 同样 98304 个真实动作，历史越长，完整历史重算和 Critic 图分块越多。第 40 轮 Critic 学习约 13.7 秒，第 46 轮约 32.0 秒；每轮 Critic 都是 393216 个标签、完整三遍。Actor 还按既有 KL 规则提前停止，实际完成的遍数也影响周期。这部分变化不能靠固定动作数量消除。
2. **原采样路径过早等待 GPU 结果。** 两组环境虽然已有流水线，主线程仍在处理上一组 CPU 环境结果前，调用 `.cpu()` 等待下一组 GPU 动作。这使环境结果解包、历史记录与 GPU 推理不能充分重叠。本次修改直接针对这个可重现的执行依赖。
3. **另有间歇性的额外延迟。** 第 29 和 31 轮历史与解码量接近，Actor 推理记录却从 13.4 秒变成 33.2 秒。第 33 轮无重启恢复；本次新版本第 58 轮也自行回升到约 1432 动作/秒。因此，现有记录不能证明每次下降都是永久降级。Windows 计数器多次记录到桌面进程占用同卡约 16%–25% 的 3D 引擎，这是竞争的相关证据，尚未通过独立对照确定全部因果。用户不能最小化窗口，所有正式测量按正常桌面使用条件进行。

目前没有发现本窗口内的 OOM、有效微批次从 32 减小、显存持续增长或热降频证据。系统可用内存充足，抽样时没有正在换入/换出。代码中的 OOM 回退仍存在，但不能把未发生的回退当成本次降速原因。

## 本次修改

- CUDA 动作结果先复制到独立的锁页主机缓冲，用 CUDA Event 标记完成；主线程先处理上一组环境响应，真正需要动作时再等待。
- 模型、缓存和随机数仍在同一线程、同一 CUDA stream 上提交。对局结束后的布局生成排在动作复制之后，保留原有随机数提交顺序。
- 只对符合条件的 CUDA 固定 KV、单动作采样使用延后等待。CPU、其他设备、单组、不支持的采样参数和拆分批次继续走现有路径。
- 增加 `rollout/actor_deferred_batches` 和 `rollout/actor_result_wait_seconds`。异步后的 `actor_inference_seconds` 是 CPU 提交加剩余等待时间，排除了重叠部分，不能把它的下降直接说成 CUDA 核函数加速。

本次代码差异保存在 `output/diagnostics/stability_20260920/source_changes.patch`，以任务开始时的工作区快照为基准，没有覆盖此前未提交的修改。

## 保持的训练约束

Actor minibatch **1024 个动作**，Critic minibatch **4096 个视角标签**，两者每个完整 epoch 都是 **96 个 minibatch**，低于 384 上限。Critic 四个视角不重复计算环境步数。

保留 30 亿真实动作预算、128 局、16 个环境进程、1000 步历史、1001 token 上限、16 层网络、个人优势和奖励、完整三遍 Critic，以及 Actor 第一遍完整覆盖、最多三遍与原 KL/LR 控制。学习器微批次保持 32。没有调整其他桌面程序或系统图形设置。
