## 动作目前怎样编码

当前 `PublicActionEncoder` 的实现是：

```text
[source_x, source_y, destination_x, destination_y, relative_actor]
             → Linear(5,256) → 一个 256 维动作向量
```

起点和终点各占两个坐标数值，行动方占一个相对编号；全部沿用已有主视角转换规则。
坐标在全棋盘上唯一，准确公式见[五维动作编码](action_linear_zh.md)。
不再创建字段 Embedding 或动作 LayerNorm，不读入战斗结果、是否攻击、被夺军旗归属、
新亮旗数量和出局人数。初始动作通过显式 presence mask 保持零向量。

实际实例化得到动作编码器 **1,536 个参数**，整盘编码器 **4,610,560 个参数**。
Policy 与 Critic 各有自己的输入编码器。此处讨论历史动作输入，当前动作的输出仍是
合法性掩码约束下的起点、条件终点两阶段概率。

## 每手棋盘的原始编码规则

每张棋盘先保存 `B=[c(0),...,c(128)]` 共 **129 个类别整数**，按观察者主视角的点编码排序。
每个整数表达该点的**可见占位、棋子所属方、已知棋种**。

| 点位区间 | 固定位置槽 |
|---|---|
| 0..29 | 自己阵地 |
| 30..59 | 左侧阵地 |
| 60..89 | 正对面阵地 |
| 90..119 | 右侧阵地 |
| 120..128 | 中央九宫 |

阵地内按 `(row-1)*5+(column-1)` 排列。棋子移动后保留所属方；不能用它目前所在的
阵地区间推断敌我。下表的归属编号来自相对玩家关系，与位置槽是两套独立编码。

| 类别码 | 含义 |
|---|---|
| 0 | 真实空点 |
| 1 | 相对玩家 1 的未知棋子（上家） |
| 2 | 相对玩家 2 的未知棋子（四国中为对家盟友） |
| 3 | 相对玩家 3 的未知棋子（下家） |
| 138 | padding，配合 point mask 使用，不是真实棋子 |

精确身份统一使用 `棋种基础码 + 32 × 相对归属`：

| 棋种 | 我方 r=0 | 上家 r=1 | 对家 r=2 | 下家 r=3 |
|---|---:|---:|---:|---:|
| 军旗 | 30 | 62 | 94 | 126 |
| 炸弹 | 31 | 63 | 95 | 127 |
| 工兵 | 32 | 64 | 96 | 128 |
| 排长 | 33 | 65 | 97 | 129 |
| 连长 | 34 | 66 | 98 | 130 |
| 营长 | 35 | 67 | 99 | 131 |
| 团长 | 36 | 68 | 100 | 132 |
| 旅长 | 37 | 69 | 101 | 133 |
| 师长 | 38 | 70 | 102 | 134 |
| 军长 | 39 | 71 | 103 | 135 |
| 司令 | 40 | 72 | 104 | 136 |
| 地雷 | 41 | 73 | 105 | 137 |

这些是类别编号，不表示连续大小。四暗开局只知道己方精确身份，其他三方使用 1/2/3；
双明开局还知道盟友精确身份，使用 94..105。按规则公开或确定推断出的身份会换成精确码。
`has_moved` 和完整 `candidate_mask` 虽然存在于环境观测结构中，但没有逐点拼入这 129 个
棋盘类别；相关历史信息由动作序列提供，确定推断后的身份会反映到最新棋盘。

两个模式使用相同种子 20260910 生成的完整合法开局 129 整数列表，已导出到
[可复算 JSON](benchmarks/encoding_hardware_scenarios_rev21_20260910.json) 的 `initial_board_examples`。
这是可复现示例；每局布阵不同，不存在所有对局共用的固定 129 整数开局。

## 从原始棋盘到历史 token

```text
129 个类别整数
  → 固定槽位 one-hot：第 j 点的类别 c 激活位置 j*139+c
  → 17,931 维棋盘类别 + 3 维模式 + 75 维规范阵亡位
  → 整个 18,009 维向量通过一次 Linear(18009, 256)
  → 一个 256 维棋盘向量 g
```

one-hot 展开没有可训练参数，不产生每个点的 256 维向量。
模式 one-hot 为四暗 `[1,0,0]`、双明 `[0,1,0]`、二人 `[0,0,1]`。
死规则关闭时移除阵亡位，线性层输入为 17,934 维；默认开启时是 18,009 维。
阵亡位开局全零；四暗按三名其他玩家各 25 位排列，双明的盟友 25 位留零。
二人使用自己的 60 点棋盘，其余点槽全零，未知对手用 2、精确身份用对家块 94..105。

历史基础 token 固定为动作在前、棋盘在后：

```text
布阵后首次：       concat(零动作 256 维, 初始棋盘 g0) → 512 维
完成第 t 个动作后：concat(本手动作 qt, 动作后的棋盘 gt) → 512 维
```

随后还会加上位置、模式、无交互计数、在场方、亮旗方、轮到谁等元数据嵌入，送入
当前 main 配置的 32 层时序网络。零动作指上述原始 concat 的动作部分；加元数据后
完整 Transformer 输入的前 256 维不要求为零。各观察者使用各自的可见棋盘和主视角动作。

## 官方硬件规格与计算口径

采用稠密 BF16、FP32 累加口径，与当前 BF16 训练对应；不使用 FP4 稀疏 AI TOPS。

| GPU | 显存 | 显存带宽 GB/s | 稠密 BF16 Tensor TFLOPS | 规格来源 |
|---|---:|---:|---:|---|
| RTX 4090 | 24 GB | 1008 | 165.2 | [NVIDIA Ada 白皮书，附录 A](https://images.nvidia.com/aem-dam/Solutions/geforce/ada/nvidia-ada-gpu-architecture.pdf) |
| RTX PRO 6000 Blackwell Workstation | 96 GB | 1792 | 503.8 | [NVIDIA RTX PRO Blackwell 白皮书，附录 A](https://www.nvidia.com/content/dam/en-zz/Solutions/design-visualization/quadro-product-literature/NVIDIA-RTX-Blackwell-PRO-GPU-Architecture-v1.0.pdf) |
| H100 SXM | 80 GB | 3350 | 989.5 | [NVIDIA H100 规格](https://www.nvidia.com/en-us/data-center/h100/) |

H100 官方网页的 BF16 1979 TFLOPS 带有稀疏性脚注，稠密值按除 2 计算。
4090 的稠密 BF16/FP32 累加值为 165.2；不能混用 FP16/FP16 累加或稀疏值 330.4。
这里的 PRO 6000 不指 RTX 6000 Ada 或 300W Max-Q；H100 PCIe/NVL 也不能直接套 SXM 行。

只有 4090 有本项目真实训练测量。为回答目标硬件工期，以下是**公开假设的敏感性情景**，
不是目标卡实测、置信区间或上下界：

1. 除存盘外的耗时中，假设 GPU 可加速部分 `f=60%..85%`。这个比例没有实测，
   也不是 GPU 利用率；现有计时的采样阶段同时包含 GPU 推理和 CPU 工作，不能直接分离。
2. GPU 部分分别按显存带宽比和稠密 BF16 算力比缩放，假设相对硬件利用程度相同。
   PRO 6000 的两个情景倍率为 1.78/3.05；H100 为 3.32/5.99。其间还有未建模的算子差异。
3. 其余 CPU、调度部分保持原成本。非存盘阶段加速为 `S=1/((1-f)+f/r)`，
   得到 PRO 6000 约 1.36..2.33 倍、H100 约 1.72..3.43 倍。
4. N 卡每卡保留 20 局和 5120 个 rollout 样本，全局并行局数/rollout batch 随 N 增加；
   单卡效率取 1，多卡效率假设 70%..90%。CPU 核数、通信和供电散热需支撑该负载。
5. 按当前每轮保存完整检查点，保留 4090 已测的单次 11.2..11.8 秒，不按算力缩短。
   多卡会汇集更多 rank 的游戏历史，真实保存时间可能增加；此处没有实测这项增长。
6. 预算为一个模式全卡合计 30 亿环境交互，80% 训练可用率。前向、反向和 epoch 不计环境步。

公式为：

```text
日历天 = [4090 非存盘总秒数 / (N * S * 多卡效率)
          + 预计保存次数 * 4090 单次保存秒数] / 86400 / 0.8
```

## 一个模式 30 亿环境交互的时间情景

下表单位为**日历天，按 80% 可用率**，数值为四暗和双明情景合并后取整。
两模式若在同一组 GPU 上依次各跑 30 亿步，需要分别相加。

| GPU | 卡数 | 按现有短测平均历史成本 | 若保持已测第二轮较长历史成本 |
|---|---:|---:|---:|
| PRO 6000 Blackwell | 1 | 369..572 | 439..715 |
| PRO 6000 Blackwell | 2 | 200..388 | 238..490 |
| PRO 6000 Blackwell | 4 | 100..194 | 119..245 |
| PRO 6000 Blackwell | 8 | 50..97 | 60..123 |
| H100 SXM | 1 | 283..471 | 330..583 |
| H100 SXM | 2 | 152..316 | 178..396 |
| H100 SXM | 4 | 76..158 | 89..198 |
| H100 SXM | 8 | 38..79 | 45..99 |

若全天连续运行，相应天数乘 0.8。现有真实训练历史最长为 512，成熟策略的大量长历史、
1000 步滑窗、调整每卡并行度后的吞吐均未验证。上述范围不覆盖所有这些不确定性。
大显存允许尝试更高每卡并发，但额外收益没有计入；显存容量不能直接当作速度倍数。

额外归档、选拔未并入表格。当前四暗 32 局完整评测外推 60 次、每次 100 局的总开销
约 9.6 小时（4090），详见[原始实测与限制](whole_board_ppo_eta_zh.md)。GPU 之间的性能
差距应最终用相同代码、相同历史分布的端到端采样与学习计时校准。
