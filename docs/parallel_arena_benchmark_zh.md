# 并行评测实测方法与结果

使用 `tools/benchmark_parallel_arena.py` 比较同一 checkpoint、相同轮转组和种子的
串行与并行评测。每阶段重新加载候选与对手模型，模型加载单独计时；比赛计时包含
布局采样、合法动作生成、模型推理、环境推进和结果整理。以完整比赛的总步数和
耗时计算吞吐，不用 32 步工程冒烟的局数/秒推算正式比赛耗时。

```bash
PYTHONPATH=src python tools/benchmark_parallel_arena.py \
  runs_ppo_sequences_20260910/four_dark/with_dead_rules/checkpoints/best.pt \
  --groups 4 --parallel-games 1 16 --environment-workers 4 \
  --max-plies 2000 \
  --output docs/benchmarks/2026-09-11_parallel_arena_4090.json
```

四国模式 `--groups 4` 表示每阶段 16 局，两人模式表示每阶段 8 局。每局正常结束或
达到相同的 2,000 步规则上限后才计入结果。工具记录每局实际步数、终局原因、结果及
完整动作序列 SHA-256，并比较串行和并行的动作与结果是否一致。独立随机数流保持
相同游戏种子的随机数输入；GPU 上不同矩阵批量的浮点舍入仍可能改变采样路径。
出现差异时同时比较实际步数/秒，不能只按完整阶段耗时宣称相同工作量的加速。

JSON 还包含：

- checkpoint SHA-256、训练更新数、完整模型配置、设备及 PyTorch 版本。
- 总耗时、模型加载耗时、局数/秒、步数/秒、父进程 CPU 时间。
- PyTorch 峰值已分配/保留显存、OOM 降批次数，以及每模型实际历史缓存容量。
- 局长、实际策略历史 token 数、实际请求批量的中位数、95% 分位和最大值。
- 超过 1,000 步的对局数量、超过 1,000 token 的策略请求数，用于识别历史窗口阶段。
- 可用时每秒采样整张卡的利用率与显存用量；这些设备数据包含桌面及其他进程。

本次使用 WSL Ubuntu 24.04、RTX 4090 24 GiB、PyTorch 2.11.0+cu130、4 个 PyTorch
CPU 线程。该 checkpoint 的 `update=0`，属于已有计时实验的初始权重；自己对弈的
胜负用于核对执行结果，不构成棋力上涨证据。

## 16 局完整比赛实测

完整原始记录见 `docs/benchmarks/2026-09-11_parallel_arena_4090.json`。两个阶段各自
完成 16 局；没有把 4 局样本乘以四。串行基线在连续对局棋盘缓存 LRU 修复前启动，
并行阶段使用最终 LRU 和按并发历史窗口扩容后的实现，因此这张表比较的是本次整体
优化结果，不能拆分成纯调度或单独缓存优化的收益。基线进程未记录源码哈希，最终
阶段记录了 `arena.py`、`models.py` 和 `rollout.py` 的 SHA-256。

| 指标 | 串行，1 局在途 | 最终并行，16 局在途、4 个环境 worker |
|---|---:|---:|
| 完成局数 | 16 | 16 |
| 比赛总时间 | 551.700 秒 | 130.036 秒 |
| 实际总步数 | 10,045 | 9,435 |
| 每秒步数 | 18.207 | 72.557 |
| 平均每局时间 | 34.481 秒 | 8.127 秒 |
| 每阶段模型加载 | 5.280 秒 | 5.259 秒 |
| 局长中位数 / 最大值 | 635 / 794 | 635 / 794 |
| 策略历史 token 中位数 / 最大值 | 331 / 794 | 316 / 794 |
| 峰值已分配显存 | 1.566 GiB | 5.975 GiB |
| 峰值保留显存 | 1.578 GiB | 6.014 GiB |
| GPU 平均利用率采样 | 37.23% | 36.36% |
| 父进程 CPU 时间 | 551.722 秒 | 168.549 秒 |
| OOM 降批次数 | 0 | 0 |

按实际步数归一化的吞吐提高 **3.99 倍**；完整阶段耗时比为 **4.24 倍**。两次有
10/16 局动作序列哈希不同，其中 3/16 局的胜负或终局原因不同，因此后者不是完全
相同棋谱的计时比。全部差异的轮转组和座位保存在 JSON 中。不同批量的浮点舍入
可能改变随机采样路径，本次又包含缓存实现变化，不把差异归因于单一原因。

并行实际请求按模型归属分批，中位数 7 条，最大 8 条；配置上限是 16 条。GPU
利用率采样没有上升，但单位时间完成的策略请求明显增加。没有通过额外启动未受限
的模型进程来追求利用率数字。两次均没有超过 1,000 步的对局，因此完整比赛计时
本身没有覆盖生产历史窗口滑动，下面单列满窗口容量测量。

比赛显存数据来自独立推理进程，常驻候选和对手的 Policy + Layout；没有常驻训练中的
Critic、参考模型、优化器状态或训练梯度，不能把剩余显存直接当作训练期间的可用空间。

满窗口容量测量另用以下命令，固定 16 条独立的 1,001-token 合成历史，先冷启动推理，
再保留初始观察、移除最早转移并追加新观察，测量两次窗口滑动。它检验完整主模型的
长历史内存和重算路径；合成棋盘不代表合法对局，不参与局数/秒或棋力统计。

```bash
PYTHONPATH=src python tools/benchmark_parallel_arena.py \
  runs_ppo_sequences_20260910/four_dark/with_dead_rules/checkpoints/best.pt \
  --parallel-games 16 --capacity-steps 3 --reserve-gib 3.5 \
  --output docs/benchmarks/2026-09-11_parallel_arena_4090_full_window.json
```

`--reserve-gib 3.5` 额外分配 3.5 GiB 设备字节张量以预留资源，属于容量探针，
不等于实际加载训练模型、优化器和梯度的端到端训练评测。

满窗口测量的原始记录为 `docs/benchmarks/2026-09-11_parallel_arena_4090_full_window.json`。
每步共 16 条请求，候选和对手各处理 8 条，采用 16 局并发对应的每模型 96 个时间缓存条目和
32,032 个棋盘缓存条目：

| 阶段 | 耗时 | 峰值已分配显存 | 峰值保留显存 |
|---|---:|---:|---:|
| 1,001-token 冷启动 | 2.884 秒 | 10.378 GiB | 11.104 GiB |
| 第一次完整窗口滑动 | 1.121 秒 | 10.779 GiB | 10.988 GiB |
| 第二次完整窗口滑动 | 1.113 秒 | 10.779 GiB | 10.988 GiB |

三次均未发生 OOM 降批。上述显存包含额外的 3.5 GiB 预留张量；主模型满窗口路径
在这次容量测量中可以运行，并不消除历史滑动的重算成本。

## 环境 worker 短测

同样 16 局并发、每局最多 128 步，分别使用 1 和 4 个环境 worker。两次都是
1,991 步，所有动作和结果 SHA-256 完全相同：1 个 worker 为 18.268 秒、
108.990 步/秒，4 个为 18.728 秒、106.314 步/秒。单 worker 仅快约 2.5%，
一次短测不足以支持改动默认值，保留 4 个 worker。原始记录分别为
`2026-09-11_parallel_arena_4090_workers1.json` 和
`2026-09-11_parallel_arena_4090_workers4.json`。这也说明纯 Python 环境线程
受 GIL 和调度开销影响，增加 worker 不能保证加速。

## 32 局并发容量与短测

在 16 局并发的容量测量留有空间后，继续测试 32 局并发，未继续扩大到 64。
先检查 32 条独立的 1,001-token 历史，仍额外常驻 3.5 GiB 预留张量：冷启动
5.778 秒、完整窗口滑动 2.134 秒；最高已分配 **16.798 GiB**、最高保留
**17.510 GiB**，未发生 OOM 降批。每模型使用 192 个时间缓存和 64,064 个
棋盘缓存条目。原始记录为 `2026-09-11_parallel_arena_4090_full_window32.json`。

然后使用相同 checkpoint、8 个轮转组（总共 32 局）、每局最多 128 步，比较 16
与 32 局并发；两阶段都使用最终缓存实现和 4 个环境 worker：

```bash
PYTHONPATH=src python tools/benchmark_parallel_arena.py \
  runs_ppo_sequences_20260910/four_dark/with_dead_rules/checkpoints/best.pt \
  --groups 8 --parallel-games 16 32 --environment-workers 4 --max-plies 128 \
  --output docs/benchmarks/2026-09-11_parallel_arena_4090_parallel16_vs32.json
```

| 指标 | 16 局并发 | 32 局并发 |
|---|---:|---:|
| 实际总步数 | 4,001 | 4,001 |
| 比赛总时间 | 37.144 秒 | 23.241 秒 |
| 每秒步数 | 107.717 | 172.151 |
| 峰值已分配显存 | 5.976 GiB | 10.699 GiB |
| 峰值保留显存 | 6.014 GiB | 10.744 GiB |
| 实际请求批量中位数 / 最大值 | 8 / 9 | 16 / 16 |
| GPU 平均利用率采样 | 36.38% | 32.38% |
| 父进程 CPU 时间 | 50.669 秒 | 29.622 秒 |

这次短测吞吐增加 **59.8%**。全部终局结果、局长及终局原因哈希一致；6/32 局动作
序列存在差异，已逐局记录。结合完整历史容量检查，32 局并发适合此次 24 GiB 设备
继续提高吞吐，但这组 128 步短测不是 32 局自然终局或 1,000 局耗时验证。1,001-token
容量测试中，32 条请求的总计算仍接近 16 条的两倍，不应把短历史的加速比例直接套用
到大量完整窗口滑动的阶段。

工具当前默认是 8 个轮转组、比较 1 和 32 局并发，下一轮完整 32 局自然终局计时可用：

```bash
PYTHONPATH=src python tools/benchmark_parallel_arena.py \
  runs_ppo_sequences_20260910/four_dark/with_dead_rules/checkpoints/best.pt \
  --groups 8 --parallel-games 1 32 --environment-workers 4 --max-plies 2000 \
  --output arena_benchmarks/full_32_games.json
```

这条命令是后续复测方法，本次没有运行它；本次完整比赛计时仍是上面的 16 局串行
和 16 局并行数据。

`2026-09-11_parallel_arena_4090_smoke.json` 仅验证 16 局并发、每局最多 32 步的
工程路径，不能用它预测 1,000 局时长。正式 1,000 局耗时还随模型、终局分布、长历史
重算比例和同机负载变化。四暗和双明应分别实测，不把一种模式的结果当作另一种模式
的性能保证。
