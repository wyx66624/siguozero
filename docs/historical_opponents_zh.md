# 后半程历史对手、队友训练与评测

这项功能用于检查模型是否持续战胜多个早期版本，并训练模型适应不同版本的队友。四暗和双明各自保存独立对手库、训练状态和评测结果。双人 GRPO 不启用这条 PPO 采样路径。

## 启用时间与快照

门槛取 `ceil(target_environment_plies × start_fraction)`，只看所有玩家、所有 rank 实际执行的环境动作数。30 亿步预算的门槛为 **15 亿步**；update 数、优化器步数和评测棋局都不会提前触发这个门槛。

前半程保存一次功能启用时的真实模型，再分别在 5%、10%、20%、30%、40% 保存早期模型，默认最多 **6 个**。跨过门槛的那个完整更新才有可保存的参数，因此记录实际环境步，而不假装拥有恰好在某一步的模型。一次更新跨过多个保存门槛时只保存一个版本。

快照包含 Policy、Layout 和必要配置，不包含 Critic、优化器、参考模型或训练棋局。文件不可变，登记 SHA-256。训练达到一半时至少需要两个真实早期版本；后补功能不会伪造已经错过的早期模型。

默认配置见 `configs/local_4090_training.yaml`：

```yaml
historical_opponents:
  enabled: true
  start_fraction: 0.5
  training_fraction: 0.2
  teammate_fraction: 0.2
  snapshot_fractions: [0.05, 0.10, 0.20, 0.30, 0.40]
  cohort_games: 1024
  eval_games: 400
  uniform_fraction: 0.05
  learning_rate: 0.01
```

## 独立的 20% 历史对手与 20% 历史队友

后半程每局指定一个使用当前模型的基准学习席位；它的对家是队友，另一队两个席位是对手。按**新开棋局数**，对手队伍为当前 / 历史版本的目标比例是 80% / 20%，队友为当前 / 历史版本的目标比例也为 80% / 20%。两种角色按乘积分配，允许重合：

| 对手队伍 | 基准席位的队友 | 新开局目标 | 当前模型控制的席位数 |
| --- | --- | ---: | ---: |
| 当前 | 当前 | 64% | 4 |
| 历史 | 当前 | 16% | 2 |
| 当前 | 历史 | 16% | 3 |
| 历史 | 历史 | 4% | 1 |

因此，包含至少一个历史席位的棋局合计是 **36%**，两个 20% 的交集为 **4%**。不能把两个维度绑成同一批 20% 棋局，也不能把它们解释为互不重叠的 40%。这里的独立性指对手 / 队友角色组合的目标分布；实现采用四类累计配额及随机打破同额选择，不是每局独立抛两次硬币。每种组合内部轮换全部四个基准席位，以避免座位偏差。每个席位只获得自己的合法观察。

同一驻留批次的历史席位共用一个冻结版本，包括队友与对手同时为历史版本的棋局。两个角色是否出现互相独立，不要求两个历史版本 ID 也独立。这保留原先一个历史模型副本的资源上限。`teammate_fraction: 0` 可以配置为仅历史对手模式。

一局的历史版本在终局前不会改变。当前学习模型按原有 PPO 更新边界冻结，采样结束后才更新参数。

为了减少小批次推理和权重搬运，训练时只驻留一个历史 Policy/Layout 副本。默认至少连续安排 1024 个混合棋局，然后停止为该版本开新局，等待包含历史队友或历史对手的未结束对局收尾，在下一次采样边界轮换。收尾期间继续采集全当前版本自博弈；三个混合类别各自累计欠额，并在下一批补齐，欠额较大时自动增大下一批。只剩历史队友的棋局也会锁定其版本。

因此，20% 是后半程新开局的累计目标，不是每个 update、正在运行棋局数、已结束棋局数或 Policy 样本数的硬比例。界面展示对手比例、队友比例、重合数量、四种组合的实际分布及胜和负，并分别统计每个历史版本作为对手和队友的结果。两列包含重合棋局，不能相加作为总局数。日志还记录待补开局配额；有限训练预算的末尾可能仍有未补齐配额。

对手质量分为 `q_i`，下一批的选择概率为：

\[
p_i=(1-\epsilon)\frac{e^{q_i}}{\sum_j e^{q_j}}+\frac{\epsilon}{K},\qquad \epsilon=0.05.
\]

仅在“历史对手 + 当前队友”的棋局结束后，按基准学习席位所在队胜 / 和 / 负取 `s=1 / 0.5 / 0`，更新：

\[
q_i \leftarrow q_i-\frac{\eta s}{Kp_i},\qquad \eta=0.01.
\]

这里的 `p_i` 固定为该批选中时的概率。容易被击败的模型逐渐降权，仍有挑战的模型获得更多机会；均匀混合项让每个旧版本保留最小覆盖率。历史队友相关结果单独记录，不参与对手质量更新，避免把较弱队友造成的失利误判成对手更强。评测的随机种子和结果也不反馈给这个采样器。分布式场景各 rank 独立调度、保存自己的采样状态，以避免每局额外通信。

历史对手的设计参考 [OpenAI Five 附录 N](https://cdn.openai.com/dota-2.pdf) 的 80% 当前策略、20% 历史策略，以及质量分抽样。独立队友混合、整批驻留、和棋 0.5 分和最低覆盖率是本项目的适配，并非逐字复现论文。

### PPO 学习归属

- 所有当前版本席位都参与学习，包括“当前对手 + 历史队友”中的两个当前对手席位。冻结对手和冻结队友只行动，动作参与真实环境计数和 GAE，但不产生 Policy 损失、策略熵奖励或布阵更新。
- 当前版本行动时，Critic 使用该行动席位的私有观察；冻结席位行动时，使用基准学习席位的私有观察连接时间轴，不把冻结席位的私有信息送入当前模型。即使基准席位已被淘汰，它仍有合法的观察历史。
- GAE 的胜负符号由相邻两个估值观察所属队伍决定。换到当前对手的回合会翻转符号，历史对手回合的估值仍在基准学习队视角。和棋惩罚按独立公共分量传播，始终不翻转。
- 优势归一化只使用当前版本动作。Critic 仍覆盖完整时间轴。布阵队列按 1 / 2 / 3 个历史席位批量取样，只回传当前版本席位的布阵结果。
- DDP 以全局学习方样本数校正梯度。某 rank 没有学习方动作时做零梯度同步；全局都没有时跳过 AdamW step，避免权重衰减误更新。
- 此功能没有增加“与初始检查点保持接近”的 KL 正则。

## 固定旧基准与后半程冻结对手集评测

当前本地 4090 配置全程每 **5000 万环境步**评测一次，包括达到 15 亿步之后：15 亿、15.5 亿、16 亿、……、30 亿。完整 30 亿预算共 60 个评测门槛；其中包含半程门槛的历史对手集评测为 31 轮。

每次评测都保存当前候选的不可变 Policy/Layout 快照；本地完整续训 `latest.pt` 按 **1000 万环境步**间隔保存，正常停止及评测前后也会保存。执行时以跨过门槛的完整更新为准，记录真实环境步；不复制同一组参数来伪造错过的中间模型。全部候选快照构成保存模型集，早期冻结对手库仍按前半程规则限量保存。

本地配置启用 **全程只观察，不进行冠军晋升**。15 亿步前固定本次迁移时的旧冠军作为基准（当前运行 update 1018），每轮 500 局；从 **15 亿步这一轮开始**，当前模型与固定早期版本逐一评测，所有历史对手**合计 500 局**，共 125 个完整四局组。6 个对手时，前 5 个各 84 局，最后一个 80 局；不会额外运行冠军比赛。各历史对手依次评测，GPU 上同时只保留一个冻结对手，仍以原来的 32 局并发推进，不增加常驻模型数或 KV 容量。

配置 `historical_opponents.eval_total_games: 500` 表示整个对手集的总局数，优先于旧的 `eval_games`（每个对手局数）。总数必须为 4 的倍数，且足够为每个冻结对手安排至少一组完整轮换。报告保存每个对手的实际局数与分配协议，中断重试只复用相同分配下已经完成的比赛。

对应 `configs/local_4090_training.yaml` 的配置：

```yaml
model_selection:
  four_player:
    interval_environment_plies: 50000000
    after_half_interval_environment_plies: 50000000
    after_half_historical_only: true
    observational_only: true
    historical_teammate_fraction: 0.5
    games: 500
    checkpoint_interval_environment_plies: 10000000
historical_opponents:
  eval_total_games: 500
```

每个四局组中，当前模型的基准席位走遍四个座位，**两局搭档当前模型、两局搭档历史模型**，每种条件都覆盖两支队伍。不同组轮换历史队友对应的基准席位。500 局严格为当前队友 250 局、历史队友 250 局；84 局的对手分为 42 + 42，80 局的对手分为 40 + 40。统计组完整分派，分项使用组内对应两局的平均。

冻结队友使用本场对手的版本，复用同一份 Policy/Layout，按实际行动座位读取其私有观察，不新增第三份模型或逐行动换权重。结果始终按基准当前席位所在队计算。两名对手的布局和基准席位布局在组内旋转复用，队友布局由其模型生成。这是联合 Policy/Layout 棋力评测；训练中的历史队友比例仍为独立的 20%，不由评测的 50% 改写。

每个对手单独报告总计及两种队友的胜、和、负、得分率 `(胜 + 0.5 × 和) / 局数` 和置信区间，并记录同协议、同对手的相邻评测分数变化。四局组是统计单位，不能把四个相关棋局当成四个独立样本。新运行给每个门槛分配 `0.05 / 60` 的显著性预算；前半程一个固定基准，后半程均分给实际 K 个对手。每个对手再将预算三等分给总分、当前队友分项、历史队友分项。已有运行保留已分配预算，不因改变频率、局数或队友协议重置统计预算。旧报告原样保存，新队友协议不与旧整队协议计算分数变化。

**全程评测只观察训练成果，不筛选是否使用当前版本。** 即使对固定基准或某个历史对手失利，也保留该轮快照，继续优化和使用后续模型。评测不回滚参数，也不改变训练对手抽样权重。训练中的质量分仍只由训练棋局更新，固定早期对手集不会被后续模型替换。

前半程报告标记 `evaluation_type: fixed_reference`，后半程标记 `historical_only`，决策均为 `use_latest`。`state.json/latest_evaluated_snapshot` 指向最新完成评测的模型；`best.pt` 保留固定旧基准。CPU 对弈全程默认使用最新可用快照，并允许手动选择旧版本。每次评测快照独立保留；最新轻量快照每 5 轮滚动更新，不代表每步都写完整断点。

确认回退指某项置信区间上界低于 50%，或低于同一对手上一轮区间的下界。没有通过统计显著性检验的结果显示“证据不足”。这些是观察提示，不是模型使用门槛；有限对手集无法证明对所有风格都变强。

评测使用训练进程中已经存在的当前模型，依次装入一个历史对手，不一次加载整个对手集。先释放训练对手副本与采样 KV，再执行评测，结束后恢复训练模型的模式、梯度开关、配置和随机状态。每个完成的对手比赛单独原子落盘；中断重试时通过双方哈希、规则协议、种子和比赛设置核对并复用。未完成的单个比赛重新执行，全部完成并提交后才更新监控的最新评测结果。后半程不会创建冠军比赛或加载冠军对手权重。

## 内存与传输限制

1. **一份历史推理权重**：只保留一个冻结 Policy/Layout，无历史 Critic 或优化器；加载文件使用 mmap。
2. **合并权重传输**：同 dtype 的所有参数共用一个连续存储，下一次切换复用同一 GPU 存储。CUDA 历史 Policy 的线性层预先转换为现有 AMP 精度，Embedding、LayerNorm 和 Layout 保持 FP32；磁盘上的冻结快照仍保持原精度。BF16 配置下每次切换为三次主要权重上传，避免逐参数或逐局搬运。转换和 128 元素对齐只在切换版本时进行。
3. **一块 KV 存储**：学习模型与历史模型共用 `游戏池大小 × 4` 个槽位。图执行和缓存内容按模型隔离；跨模型复用同一席位会明确报错。历史窗口变化仍按原有完整前缀规则重建。
4. **先释放再学习**：两种策略的 KV 和图引用一起释放，再建立 Critic 推理及优化器计算，避免退休缓存继续占用显存。
5. **布阵与动作批量化**：按模型归属组织动作批次；历史布阵有独立的小型预生成队列。不会为每局、每步从 CPU 换入权重。
6. **评测也使用打包权重**：候选模型复用、对手顺序加载、完整轮换组并行执行。显示服务只读两份小型 JSON，不加载模型文件。
7. **复用图预热流**：时序解码和动作采样共用每线程、每设备一条 CUDA 预热流，避免每种形状、每轮重新创建流。PyTorch 2.11 会按 cuBLAS handle / stream 保留工作区，见[官方说明](https://docs.pytorch.org/docs/2.11/notes/cuda.html#cublas-workspaces)。这个缓存不持有模型或 KV 张量。

断点保存包含对手与队友身份、基准席位、随机状态、质量分、四类配额与结果、座位轮换、布阵队列和未结束棋局。恢复后按原版本继续。半程前的旧版调度状态可以自动升级，不改写旧检查点；已进入半程的旧版状态不能直接切换到队友混合，需要显式迁移。恢复较早检查点时，磁盘上来自之后更新的快照会退出有效对手库，保留原文件以防误删。启用历史棋局后暂不支持改变分布式 world size 来重分片正在运行的历史对局；多机需要共享或同步同一组带哈希的冻结文件。

## 验证与性能边界

自动测试覆盖半程门槛、快照上限、权重存储复用、降权与最低覆盖率、四类联合配额和重合比例、每类四席位轮换、三个混合类别的欠额补齐、完整训练状态恢复、队友结果与对手难度隔离、真实采样时间轴中的胜负 / 和棋 GAE、梯度与熵屏蔽、双进程空样本同步、共享 KV 的窗口滑动一致性、逐对手评测及中断复用、页面显示。

本次验证：Python 全套 321 项中 314 项通过、7 项跳过（CPU 环境）；另行在 RTX 4090 上执行的 2 项共享 KV / CUDA Graph 数值测试通过，覆盖仅历史队友、仅历史对手、两者同时存在；页面的 6 项 Node 测试全部通过。真实第 474 轮检查点的 96 局状态成功恢复，调度状态从 version 1 升级到 version 2；验证未启动正式训练、未改写检查点，只刷新显示服务的历史角色元数据。

预转换主要节省约 34% 的冻结权重显存与传输量；这组短测中速度差异很小，不能宣称显著加速。混合推理相对纯自博弈仍慢约 **61%**，包含两个模型各自的小批次执行与图建立开销。该数字不是整轮训练的减速比例。KV 按完整 1001 步窗口、384 个槽位分配了约 11.73 GiB，但实际回放最长只有 64 步，因此验证了完整 KV 容量，没有覆盖长窗口重建时延。每轮诊断都会释放缓存，并核对释放后额外分配低于预设的 256 MiB 容差。

复现命令（只运行独立诊断）：

```bash
PYTHONPATH=src python tools/benchmark_historical_opponents.py \
  --checkpoint runs_local_4090/four_dark/with_dead_rules/checkpoints/latest.pt \
  --waves 64 --output /tmp/historical_optimized.json
# 加 --teammate-fraction 0 对照仅历史对手；加 --matrix-fp32 对照原精度矩阵。
```

冻结矩阵转换通过 CPU AMP 输出精确比较，以及 CUDA Graph、共享 KV、窗口滑动下与独立 FP32 权重模型的 AMP 数值比较。诊断前后核对源码哈希；正式检查点只读并复制，不会改写。

这项诊断不执行正式训练或保存训练参数。它验证内存上限与推理开销，尚不能代替包含优化器、环境收尾、长窗口和周期评测的完整训练 A/B，也不能据此承诺 20 天完成。30 亿步在 20 天完成需要包含这些开销的平均吞吐至少约 **1736 环境步/秒**。
