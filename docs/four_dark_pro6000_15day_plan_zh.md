# 四暗单张 PRO 6000、15 天完成 30 亿环境步的优化方案

2026-09-11。目标卡按 RTX PRO 6000 Blackwell Workstation Edition 96GB、600W 理解，
不是 RTX A6000 或 RTX 6000 Ada。型号规格见 [NVIDIA](https://www.nvidia.com/en-us/products/workstations/professional-desktop-gpus/rtx-pro-6000/)。
这是依据当前源码和 4090 已有剖析制定的方案与验收预算，尚无目标卡或新架构的性能实测。
候选架构尚未写入生产训练配置；保存策略已按后续要求改为仅评测时保存。

后续实现进度：第一阶段的数组历史、批量编码/动作损失、固定席位 KV、多 token
增量推理及 CUDA Graph 已完成，4090 同检查点完整训练轮实测约 2.93 倍加速，
见[实现与数值验证](ppo_pipeline_optimization_zh.md)。本页的 Critic 后补算、共享骨干、
循环记忆和浅层架构仍为候选；15 天目标尚无 PRO 6000 实测支持。

正式批量的后续[时间复测](four_dark_optimized_training_eta_zh.md)为：同起点一轮约
3.70 倍加速，48 局连续四轮约 237 步/秒，30 亿步约 147 天连续运行（RTX 4090）。
本页下方以 50.1 步/秒等旧速度作比较的预算保留为原方案背景。

## 用完整环境步吞吐定义目标

30 亿指所有席位累计的实际环境动作。额外处理四种观察、重复 PPO epoch、反向重算，
均不能增加计数。15 天完成要求：

| 可运行时间比例 | 训练运行时完整流程吞吐 |
|---|---:|
| 100% | 2315 环境步/秒 |
| 90% | 2572 环境步/秒 |
| 80% | 2894 环境步/秒 |

因此按 **至少 3000 环境步/秒** 验收。相对当前 48 局 4090 的 50.1 步/秒，需要约 58 倍
完整流程吞吐。这不是单靠增加参数压缩比例或换卡就能承诺的结果。

还有两项容易被忽略的限制。当前 PPO 收集器逐个棋局执行 Python 规则推进；48 局主要
实现了神经网络批量推理，不等于规则同时在 48 个 CPU 核上推进。原始剖析的启动脚本
每轮保存一次；现已取消，改为每 5000 万环境步评测时保存，不能沿用旧存盘摊销预测新耗时。

若保持已有每步成本、48 局/每轮 12288 步和每轮存盘节奏，单独外推 30 亿步：

- 环境推进计时块约 41.6 天连续运行，包含历史维护及终局重置等工作。
- 存盘摊销约 16.0 天连续运行。
- 两者串行合计约 57.6 天连续运行，按 80% 可用时间约 72 天。

这是保持旧开销的反事实算术，不是优化后的耗时预测。它说明要达到 15 天，必须同时
优化规则并行、重置布阵和保存节奏；它们不能在网络提速后继续维持原样。

## 第一阶段：优先保留现有模型和学习语义

### 1. 将独立 Critic 从逐步行动路径移出

当前 PPO 的动作由 Policy 选择，Critic 的值只用于随后计算 GAE、价值目标和 old value。
采样期间两个网络权重冻结，因此可以先采完整轨迹，随后对所有历史前缀的决策位置及
收集边界 bootstrap 状态批量计算 Critic，再运行原有 GAE。

顺序变为：

```text
仅 Policy 批量采样 → 完整轨迹/奖励/动作/old log-prob
→ 冻结 Critic 批量补算 old value 与 bootstrap
→ 原 GAE → 原 PPO 学习
```

这将逐步价值推理改为适合 GPU 的整段计算，并去掉采样阶段 Critic 的长历史 KV。
收益不是将原 Critic 时间全部删除：其工作转为批量推理，仍须计时。固定轨迹上应核对
逐位置 value、bootstrap、GAE 和最终损失；BF16 的不同计算路径需使用适当数值容差。
在价值补算完成前不能更新 Critic。此路线与后面的共享骨干路线是替代选择，不能将
两者节省的同一份 Critic 成本相乘。

### 2. 原始轨迹数组化，缓存键改为固定身份

- 原始棋盘码、动作、阵亡信息等在发生时写入预分配的连续数组；样本保存轨迹/席位/
  起止位置索引，避免不断构造整条历史 tuple。
- 非分支 PPO 使用棋局实例 ID、席位、历史版本/位置和权重版本定位缓存；重置棋局时
  更换实例 ID，权重更新时使旧神经缓存失效。若支持分支，另保留不可变前缀节点身份。
- 不再为每次字典查找递归哈希整条棋谱。缓存键仍必须正确区分观察模式、阵亡特征和
  窗口语义，不能只按棋盘外观或容易重复使用的 slot 编号检索。
- 原始整数特征可在多个 epoch 和两个模型之间复用；可训练编码结果不能随意 detach
  后跨 optimizer step 缓存，否则会改变历史梯度或使用旧权重特征。

### 3. 去掉逐记录小张量与逐行切片的计算图

在采集时批量构造原始字段；学习用统一 gather 形成模型输入。整盘投影结果保持为
二维张量，用索引完成去重恢复，移除逐行 select→Python list→stack 的路径。
动作 log-prob、合法动作分组和熵使用批量张量/分段归约，指标汇总后再回 CPU。

当前棋盘的 one-hot 加 Linear 还能作数学等价的改写：

```text
z = bias + sum_p W[:, p * vocab_size + piece_code[p]]
    + W_mode[:, mode] + W_dead @ dead_bits
```

只累加实际有效位置，保留空格与 padding 的区别。可使用按位置的 embedding-bag 或融合
查表求和，避免构造 18009 维稀疏向量后再做稠密乘法。参数数量和函数可以保持不变；
需核对权重/优化器布局映射、输出及梯度。这个局部节省不能直接作为整模型加速倍数。

### 4. 按 PPO 的实际访问方式组织 GPU 推理

- 每个活跃棋局/席位维护固定缓存槽。PPO 没有搜索分支，不必沿用通用多代前缀 LRU/COW
  作为唯一实现；直接使用上次有效位置和已观察的新增记录。
- 某席位漏过的 2–4 个已知动作可以一次送入各层，用正确的前缀/新增 token 因果 mask
  计算，减少逐 token 的 32 层 Python 调用。不能并行假设尚未执行的未来走棋。
- 使用静态连续 KV 或真正直接读取分页 KV 的内核，减少每层取页后再次拼装 K/V。
- 稳定批量形状、固定工作区，分别编译推理和学习的张量函数，再测试 CUDA Graphs。
  `torch.compile` 不能自动消除 Python 游戏对象、整个历史哈希和所有动态控制流。
- 当前满 1000 步后的窗口滑移会破坏精确前缀。保持现有语义时仍须正确重算，不能仅
  用循环缓冲就宣称输出等价；要持续消除这笔成本，需要明确改变流式记忆架构。

[PyTorch 推理分析](https://pytorch.org/blog/accelerating-generative-ai-2/) 和
[LeanRL](https://github.com/meta-pytorch/LeanRL) 展示了编译、图捕获与数据搬运优化的方法。
其他任务的倍数不能套到本项目，更不能与本项目其他单项收益机械相乘。

## 第二阶段：以 15 天为优先约束时的架构候选

我建议优先验证共享骨干的 Recurrent PPO，另保留浅层 Transformer 作棋力/吞吐对照。

```text
棋盘 128 + 动作 128
        ↓ 拼接 256、投影到 512
共享编码及记忆
        ├─ 策略头：合法动作概率
        └─ 价值头：当前观察下的局面价值
```

| 项目 | 优先验证：循环记忆 | Transformer 对照 |
|---|---|---|
| 共享编码 | 4 个残差 SwiGLU 块，宽 512、FFN 1024 | 8 层，宽 512、8 heads、FFN 1536 |
| 记忆 | 2 层 GRU，hidden 512 | 先保留完整历史以便对照；流式记忆需另行定义 |
| 策略+价值参数，合计 | 按所列模块约 1212 万 | 按所列模块约 3048 万 |
| 主要收益来源 | 不再每次查询整段时序注意力；当前隐状态固定大小 | 减少层间串行与调用，使用更大的矩阵 |
| 关键代价 | 历史被压缩、时间梯度截断，需验证隐信息棋力 | 仍有历史输入/缓存成本，15 天把握更低 |

以上参数是候选模块的算术统计，不是已经实现或测试的模型。布阵 1729 万参数及冻结
布阵参考副本未计入“策略+价值”列。1212 万并非保证足够强，3048 万也不保证更强。

共享骨干让 Critic 仍然存在，但成为共同特征上的价值头。一次前向产生两类输出，一次
联合损失反向更新共同参数；不能再用两个独立 Adam 分别修改同一骨干。每个联合 epoch
同时覆盖策略和值的目标，收益不是将原两个网络的梯度更新数原样换个名字。

循环记忆训练建议从连续 128 个公共时间步的片段开始，前置 32 个时间步用于恢复隐状态
（burn-in，不计策略损失），再测试 64/128/256 的学习片段。每个席位分别持有隐状态，
每次公共行动更新其应看到的观察，仅实际行动席位的决策位置参与策略损失。
因此每个环境步仍可能有四个观察位置的网络工作，不能虚增环境步数或偷掉其他观察。

128 步反向跨度不等于运行时只记得 128 步：GRU 可携带更早的摘要，但摘要不是旧历史
的无损副本。应保存片段初始隐状态，保持时间顺序、终局/淘汰 mask，处理权重变化后的
隐状态陈旧问题，并保留当前团队视角与 GAE 符号约定。不同席位不能混用隐状态。
公开可见的身份揭示、是否移动过、交战记录等可保留显式信息摘要，不能输入对手暗子真值。
[TorchRL 循环状态说明](https://docs.pytorch.org/rl/stable/reference/recurrent_state_lifecycle.html)、
[Recurrent PPO 的方法与限制](https://arxiv.org/abs/2205.11104)

共享、改宽度或换成 GRU 都不是严格断点续训。可迁移兼容的编码层，或用可用的旧模型
进行蒸馏初始化，在新训练目录中重新建立优化器状态，并保留旧 checkpoint 作对照。
迁移/性能开发时间不包括在下面的一次正式训练 15 天吞吐预算内。

## 主机与批次必须配套

- 并行局数从 256 起测，再测 512；1024 是容量与吞吐候选，不是默认保证更快。
- PPO 收集器实现真正的多进程/原生并行规则推进。按可用 CPU 资源测试 8/16/32 workers；
  当前收集器没有使用 GRPO 路径的环境线程参数，只调 YAML 数字不会得到同样并行效果。
- 规则、合法动作与观察生成的热循环可移到 C++/Rust/编译内核；多个游戏用共享内存数组
  通信，避免大量游戏对象序列化。GPU 处理另一批棋局时让 CPU 推进上一批。
- 布阵和终局重置批量化；整个 rollout 使用同一行为策略版本，不能为追求异步而混入
  不受控制的旧策略数据。
- 学习先增加可容纳的序列微批；若将 optimizer minibatch 从 512 改到 2048/4096，应
  单独验证 KL、价值拟合和棋力。微批和优化器批次不是同一概念，增大后者会改变优化。
- 在局部显存验证后关闭不必要的激活重算；不是因为卡有 96GB 就一次放入任意批次。
- checkpoint 仅在需要评测时保存，默认每 5000 万环境步触发一次，然后与此前最优旧模型
  对弈 100 局。在完整更新边界、评测前后各原子写入一次完整续训快照；平时及退出时
  不额外保存。中断后从最近评测保存点恢复；新运行首次评测前的进度尚未落盘。
  具体比较规则和恢复约定见[自动最优模型选择](best_model_selection_zh.md)。

## 可验收的时间预算，不使用假设倍率代替实测

一个具体设计起点：256 局 × 每局采样 128 个环境动作 = 32768 个新环境步/轮。
四席位观察约 131072 个输入位置，未计 burn-in；PPO 联合训练先保留 3 epoch。

| 每轮阶段 | 目标上限，尚未实测 |
|---|---:|
| 采样：策略/值输出、规则推进、观察、重置 | 5 秒 |
| 学习：全部 3 epoch、反向、优化器更新 | 5 秒 |
| 额外布阵学习、保存、评测等摊销 | 1 秒 |
| 合计 | 11 秒 |

这对应约 2979 环境步/秒，30 亿步按 80% 可用时间约 14.57 天。**11 秒是验收要求，
不是预测该配置已经能达到 11 秒。**

| 实测完整流程吞吐 | 30 亿步、80% 可用时间 |
|---|---:|
| 1000 步/秒 | 43.4 天 |
| 2000 步/秒 | 21.7 天 |
| 3000 步/秒 | 14.5 天 |
| 4000 步/秒 | 10.9 天 |

验证顺序是：同轨迹数值/梯度等价性 → 包含长局和终局重置的完整流程 → 目标 PRO 6000
上跨多次布阵学习/保存/评测的持续测量 → 固定对手池、多布阵和换座位的棋力对照。
对于改变架构的路线，比较相同墙钟预算下的棋力，而非要求它逐层等价于旧模型。
达到 3000 步/秒证明能在预算内完成交互数量，不证明 30 亿步后必然达到某个棋力等级。
