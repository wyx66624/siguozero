# 四暗 3632 万参数 PPO 为什么训练很慢

2026-09-11。对象为当前四暗 main：棋盘/动作各 128 维、时序 256 维、32 层、FFN 1024、
最多初始状态加 1000 个历史动作，独立 Policy/Critic，各 3 个 PPO epoch。

当前慢同时包含两件事：每次环境交互对应的网络工作量远多于一个预训练 token；
实现还花了大量时间处理小批次、历史数据和张量搬运。参数量小不代表调用次数少，
但也不能用强化学习的额外成本证明必须训练数百天。

## 可靠的完整流程计时

本次重新核对了 [48 局基准原始记录](benchmarks/parallel_games_48_four_dark_rev22_4090_20260911.json)。
模型、历史编码、训练器源码 SHA256 均与该记录一致。只使用已有来源核查支持的第 3、4 轮；
前两轮受到并发测试影响而排除。每轮 12288 次实际走棋，主机 RTX 4090 24GB。
阶段时间包括各自 Python/框架与等待开销，不能当作纯 GPU 算术时间。

| 阶段 | 平均秒/轮 | 占完整流程 |
|---|---:|---:|
| 策略网络采样推理 | 65.82 | 26.84% |
| 价值网络采样推理 | 64.80 | 26.42% |
| 策略网络学习 | 49.55 | 20.20% |
| 价值网络学习 | 43.59 | 17.77% |
| 环境推进与该计时块内的历史维护、终局重置 | 14.72 | 6.00% |
| 每轮一次 checkpoint 摊销 | 5.66 | 2.31% |
| 其余调度、优势处理等 | 约 1.13 | 约 0.46% |
| 合计 | 245.27 | 100% |

采样网络占 53.3%，两个网络学习占 38.0%。规则模拟不是最大的瓶颈。即使把环境推进和
存盘耗时全部消除，按这个窗口也只有约 1.09 倍整体加速。若只把采样网络加速一倍，
整体约加速 1.36 倍。因此需要同时优化采样和学习。

这两轮加存盘约 50.1 环境步/秒，对 30 亿步的机械外推为约 693 天连续运行，按 80%
运行时间折合约 866 天。它不是合理训练工期、硬件性能上限或达到强棋力的必要时间；
没有覆盖长期棋谱分布、所有滑动窗口情况、周期性布阵学习和选拔。此前按显卡峰值和
假定多卡效率制作的时间表不能作为已验证的排期或采购依据。

## 30 亿走棋不是 30 亿预训练 token

当前计数在实际 `game.step()` 时增长；网络读取历史、PPO 重复学习、梯度重算不增加该计数。
本 PPO 收集路径没有额外 GRPO 分支或树搜索。30 亿步指所有训练席位累计 30 亿次走棋，
不是每个席位各 30 亿，也不是总共只处理 30 亿个网络输入位置。

实际模型参数为：Policy 36,324,226，Critic 36,208,897，Layout 17,292,288。
策略和价值不是仅多一个输出头的共享骨干，而是两套独立骨干。每步采集需要二者推理，
采集后各训练 3 个 epoch；布阵模型另有较低频率的训练，不能算成每一步都训练。

如果两个网络均跑满 3 个 epoch，30 亿环境决策对应 180 亿次决策样本呈现，尚未计入
历史输入和反向重算。这里的“样本呈现”不是 180 亿次独立模型调用；前缀合并已经生效。
PPO 多 epoch 本身是算法允许的数据复用，不能将它等同于无效训练。
[PPO 原论文](https://arxiv.org/abs/1707.06347)

预训练通常从已有文本批量读取序列，一次前向同时给许多位置计算损失；在线自对弈还要
按行动顺序生成新数据。四暗同一副棋有四种玩家观察，返回某位玩家行动时，其历史通常
已新增多个公共动作。权重更新之后，推理缓存也必须按新权重重建。

当前采样有 KV cache，学习有同前缀的多位置损失，不能再声称每步总把 1000 个历史位置
全部从头重算，也不能把已经启用的优化重新列为预期加速。在采用的 48 局第 3、4 轮里，
策略采样共执行 235459 次历史棋盘编码，除以 24576 个环境决策约为 **9.58 次编码/决策**；
这是采样策略网络的统计，尚未包括 Critic 和学习，不是固定的 token 或 FLOPs 倍率。

对于普通 dense Transformer 预训练，常用粗估为 `C ≈ 6ND`。3632 万参数、30 亿训练 token
按此约为 `6.54×10^17 FLOPs`；这里的 D 是实际训练 token，不能把环境步数直接代入。
该近似也不能充分描述本模型的长历史注意力、预处理、缓存和 PPO 重复学习。
[Chinchilla 论文的 FLOPs 说明](https://arxiv.org/html/2203.15556v1)

## 已确认的实现路径

1. **缓存键本身反复遍历完整历史。** 时序缓存键是 `(mode, state.records)`，而 records 是
   嵌套的不可变记录元组。前缀查找至多尝试 9 次，每次仍需对历史记录及内部棋盘数据做
   哈希。限定查找次数没有使哈希本身变成常数成本；生成的记录 `__hash__` 也没有缓存。
   新剖析直接观察到大量此类调用，详情见下表。
2. **增量采样被拆成很多小调用。** 名义 batch=48，但上述两轮每次增量 token 批量平均
   约 20.4；两轮策略侧共有 4424 个增量 token 批次。代码按前缀长度桶和缺失 token 数量
   分组，而当前长度桶覆盖 1001，缺失数量差异与冷状态仍会拆批。缺失几个 token 时又
   逐个 token 运行 32 层。Critic 重复走独立的同类路径。
3. **KV 的页面存储不等于直接分页注意力内核。** `PagedKVCache.decode()` 每层先
   `index_select` 取出相关历史页，整理连续 K/V，再调用 SDPA。KV 已避免重复计算旧位置
   的网络特征，但这里仍有历史搬运、临时张量和算子启动成本。
4. **学习前处理仍逐条遍历历史。** `collate_policy_states()` 用 Python 双重循环逐个历史
   记录创建小 tensor、写棋盘/阵亡/动作字段。原始棋盘仍是 129 个位置及额外字段，隐藏
   宽度减半没有使这些循环减半。
5. **整盘编码后又逐行拆开再拼接。** `_encode_full()` 将每个棋盘投影结果逐行放入列表，
   再 `stack/index_select/index_copy` 回历史序列。训练时这些切片也进入 autograd，增加
   反向操作。该路径需要针对张量整批实现做验证，不能仅靠减少模型参数解决。
6. **32 层、微批 8 条序列、激活重算。** 宽度下降减少了矩阵乘法，却没有减少层数、
   Python 循环或调用次数。每个网络均启用 activation checkpointing，反向还重放前向。
   采样阶段占用的大量 KV 显存不会自动让学习阶段的微批变大。
7. **CPU/GPU 同步和未编译的执行。** 动作、价值回到 CPU 后才推进棋局，采样与学习也
   按阶段串行。损失指标逐项转 Python 浮点数，部分路径还有 GPU `nonzero()`/`tolist()`；
   当前未启用 `torch.compile`。这些位置需要减少非必要同步并测试图捕获，不能直接许诺
   开一个开关就获得某个倍数。

这些路径在源码中可以确认；各自的耗时贡献须以下面的新版短剖析及后续相同输入 A/B
验证。小批次的启动开销、编译/静态缓存注意事项见
[PyTorch 官方推理分析](https://pytorch.org/blog/accelerating-generative-ai-2/)，同步说明见
[PyTorch 性能指南](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html)。

## 本次隔离剖析

使用 [诊断工具](../tools/profile_compact_ppo_bottlenecks.py) 从此前隔离基准的第 4 轮 checkpoint
读取模型、优化器状态和 40 局持续棋局，采集有限的新轨迹，再对同一批次反复做梯度计算，
不执行优化器更新。40 局是保存棋局池的尺寸，因此该剖析不替换 48 局完整流程计时。

首次诊断脚本遗漏 `policy.eval()`，导致策略采样缓存未启用，该组记录已标注无效并排除；
正式训练器在采样前有正确的 `eval()`，没有据此认定正式训练存在同样问题。
修正版本显式检查两个网络均处于评估模式。最终剖析见
[原始 JSON](benchmarks/compact128_bottleneck_profile_4090_20260911.json)。

修正后的运行已完成并正常退出：10240 个真实动作，平均历史 334.9、最长 751；仅采样
98.46 秒，策略推理 44.97 秒、价值推理 43.51 秒，两者 KV cache 均实际启用，实际 batch=40。
该采样速度约 104 步/秒，不含学习和保存，不能与完整流程 50.1 步/秒直接比较。
源 checkpoint 的大小及修改时间没有变化，没有其他 Python GPU 训练进程同时运行。

**新版数据确认了大量框架与历史处理工作。**

| 被测操作 | 实际观察 |
|---|---|
| 40 步暖缓存采集，含边界价值估计 | 未插桩 0.412 秒；Torch profiler 下 0.542 秒 |
| 上述采集的 GPU kernel/copy/memset 事件 | 14397 个；累计服务时间 0.100 秒 |
| 上述采集的 Python 剖析，邻近下一批 40 步 | 记录 `__hash__` 348733 次；内建 hash 749629 次，调用层级嵌套 |
| 512 个真实决策，单模型单 epoch | 合并为 12 条历史、5071 个真实输入位置，补齐后 7800 个位置 |
| 该 512 样本批次的策略前后向 | 暖机后 0.617 秒；Critic 为 0.516 秒 |
| 该 512 样本批次的 Python 剖析 | `collate_policy_states` 2 次，累计 0.216 秒；`torch.as_tensor` 15201 次 |
| 其中 128 样本策略前后向 | 未插桩 0.229 秒；Torch profiler 下 0.361 秒 |
| 上述 128 样本的 GPU kernel/copy/memset 事件 | 10269 个；累计服务时间 0.037 秒 |
| 上述 128 样本的算子调用 | `aten::select` 28649 次；`aten::copy_` 16944 次，包含 CPU 和 GPU 路径 |
| 上述 128 样本的部分 GPU 时间 | `copy_` 8.36 ms；`mm` 5.23 ms；`addmm` 1.70 ms；融合注意力前后向 7.87 ms |

CPU/Torch profiler 都改变运行时间：512 样本的 Python 插桩操作约 1.056 秒，而非原始
0.617 秒。因此不能把剖析内某函数的比例直接当作正常运行比例，也不能用 CUDA 服务
时间除以另一轮未插桩耗时来计算真实利用率。上述 CUDA 时间包含复制、注意力等，
不是 Tensor Core 利用率；事件数量也不是完整神经网络的调用数量。
但频繁哈希、逐条构造张量、切片反向和小内核已经有直接证据，不再只是参数量推测。

512 样本的前缀合并已经节省约 97.6% 原本重复的历史输入，仍有 `5071/512 ≈ 9.90`
个历史位置/决策/模型/epoch，并有约 35% 的时序 padding。若仅用这批比例举例，
30 亿步乘两个模型各 3 epoch，会形成约 **1783 亿次历史位置输入**，含 padding 则约
2742 亿次；这还没计采样、反向和激活重算。它是本批次的条件示例，不是全程固定倍率。

128 样本 profiler 识别的主要矩阵 FLOPs 约 `5.60×10^11`，部分融合注意力等未计入。
按两个相近骨干、各 3 epoch 举例约 26.2 GFLOPs/环境决策，30 亿步约 `7.9×10^19 FLOPs`，
仅为本批学习负载的粗略放大，没有计采样。这已经远大于将“3632 万 × 30 亿 token”
直接代入 `6ND` 的工作量，但仍不是数百天墙钟时间的必然原因。

**同一批 512 样本的激活重算对照：**

| 策略前后向 | 暖机后耗时 | 峰值分配显存 |
|---|---:|---:|
| 当前开启 activation checkpointing | 0.617 秒 | 1.592 GiB |
| 诊断中临时关闭 | 0.537 秒 | 4.884 GiB |

这批数据关闭重算只减少约 12.9% 耗时，前向损失指标一致。其余前处理、哈希、切片和
调度仍存在；不能承诺通过关闭重算大幅缩短全程。本对照最长 712 个历史 token，不是
满窗口的容量验证，也没有比较梯度逐项一致性或执行优化器更新。诊断结束后恢复配置，
生产配置没有改变。

## 优化验收方向

先为不可变记录与历史前缀设计可复用的精确缓存键，避免重复遍历整条历史；同时优化
原始历史批量整理、整盘编码结果的整批重组、增量 KV 的直接读取和小算子合并。
缓存键必须保留视角、模式、阵亡特征和窗口语义，并做等价性验证。这些可争取保持
现有模型及训练语义。随后在相同真实样本和损失位置上对照微批、
选择性重算及编译，最后用完整 PPO 环境步/秒复验。已经有的 KV 与前缀合并继续保留。

共享 Policy/Critic 骨干、改变层数/宽度、缩短历史、减少 epoch 等属于另一类选择，会改变
模型或训练方式，需要棋力对照；本次诊断没有应用这些变更。

例如 30 亿步在每天 80% 时间运行时，90 天完成要求完整流程约 482 步/秒，30 天要求
约 1447 步/秒。这是验收目标，与“某张显卡一定能达到”或“必须训练满 30 亿才会强”不同。
